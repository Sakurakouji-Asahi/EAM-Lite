# Depreciation Calculation Specification V1.1

本文件是 EAM-Lite V1.1 折旧引擎的规范性计算口径。方法名称不构成实现说明；公式、日期边界、舍入、尾差、确认、冲销和示例均必须一致。EAM-Lite 是固定资产辅助核算，正式凭证仍在用友 T+ 人工完成。

## 1. 统一符号与真源

| 符号 | 含义 |
|---|---|
| `C` | 原值 original cost |
| `S` | 当前残值金额 salvage value |
| `I` | 已确认累计减值余额 |
| `AD` | 已确认实际累计折旧 |
| `BV` | 实际账面价值，`C - I - AD` |
| `DB` | 当前剩余可折旧金额，`max(BV - S, 0)` |
| `N` | 初始预计折旧月数；年数总和法另定义年数 |
| `U_total` | 工作量法预计总工作量 |
| `U_period` | 当期已确认工作量 |

数据真源：

- 实际累计折旧只等于已确认 `DepreciationEntry.amount` 的代数和。
- 期初实际累计折旧在初始化确认时生成唯一 opening 分录，不以可编辑字段重复累加。
- 草稿批次、计划金额、理论测算、Excel 导出值和页面缓存均不属于实际折旧。
- `TheoreticalDepreciationRun` 只保存带参数快照的参考结果，永不自动覆盖实际账面数据。
- 减值通过已确认 `AssetValueAdjustment` 进入 `I`，不是折旧分录。
- 减值/减值转回记录保存正数幅度，`I = 期初减值 + 减值 - 减值转回`；折旧调整才以有符号金额进入 `DepreciationEntry`。冲销必须取原财务效果的精确相反数，不重新估算。

数据库、API、导入和测试使用统一机器值：`posting_period in (monthly,yearly)`；`salvage_mode in (rate,amount)`。不得另造 `month/annual/percentage/fixed` 等同义 token。rate 对应 `salvage_rate`，amount 对应 `salvage_amount`，两组字段严格互斥。

任意时点必须满足（允许显示层 0.01 的最终量化差异）：

`BV = C - I - AD >= 0`，且普通折旧后 `BV >= S`。若减值使 `BV < S`，折旧立即为 0，并提示财务先复核/变更残值估计；系统不得通过负折旧自动修复。

## 2. Decimal 与舍入

1. 所有输入先转十进制字符串构造的 `Decimal`，禁止经过 float。
2. 计算上下文精度至少 28 位；比率和中间值计算过程中不提前量化到 2 位。
3. 对外金额和实际入账金额统一：

```python
amount.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
```

4. 负数冲销同样使用 `ROUND_HALF_UP`；反向分录直接取原确认金额的相反数，不能重新跑公式。
5. 每期先算未舍入候选值，再量化当期值，最后应用残值地板和尾差校正。
6. 比率不得先显示为百分比再反算；数据库保存完整 Decimal，页面可格式化显示。

### 2.1 通用封顶与尾差

普通当期折旧：

`posted = min(ROUND_HALF_UP(max(raw, 0), 2), DB_before)`。

在预计寿命的最后一个有资格期间，或工作量达到预计总量的当期：

`posted = DB_before`。

这条最后一期校正规则优先于普通舍入，确保最终 `BV = S`，不会多提、少提或产生负净值。最后一期金额可能与前期标准金额相差数分钱，必须在计算快照标记 `final_period_correction=true`。

例：原值 10,000.00，残值 500.00，36 个月，月原始额 263.888…；前 35 期各 263.89，共 9,236.15，最后一期必须为 263.85，最终净值 500.00。

## 3. 残值、可折旧基础与初始化

### 3.1 残值

- 百分比模式：`S = ROUND_HALF_UP(C × salvage_rate, 2)`。
- 固定金额模式：`S = configured_salvage_amount`（已经是 2 位金额）。
- 必须满足 `0 <= S <= C`。
- 当前默认残值率 5% 来自选中的版本化 DepreciationPolicy（未单项指定时由公司当前默认政策解析），不来自 SystemSetting，也不写死在公式。

残值、使用年限或方法变更只对未确认未来期间生效，见第 12 节。

### 3.2 新资产

新资产起算前：`AD=0`、`I=0`、`BV=C`、初始可折旧基础 `C-S`。

### 3.3 旧资产承接

旧资产初始化必须录入或确认：原值、残值、实际期初累计折旧、期初减值（如有）、期初账面价值和接续起点，并校验：

`opening_book_value = C - opening_actual_AD - opening_impairment`。

差异超过 0.01 时不得确认。实际 opening 分录一经确认即锁定。

系统可另跑理论历史折旧，显示“理论累计折旧”，但差额只供财务判断；不得自动生成调整、覆盖 opening 分录或把旧资产当新资产从零开始。

## 4. 起算日期与期间边界

日期按 `Asia/Shanghai` 的业务日期解释。使用半开区间 `[start, end)`：起始日计提，终止日不计提。

### 4.1 起算规则

| `start_rule` | 折旧资格起点 |
|---|---|
| `current_month` | 达到可使用状态所在月 1 日 |
| `next_month` | 达到可使用状态的次月 1 日（公司当前默认） |
| `specified_month` | 财务指定月份的 1 日 |
| `specified_date` | 财务指定日期，当日开始 |

指定值不得早于可使用状态日期，除非是带原因和权限的旧资产初始化。起算日期确认后，如已有实际折旧，不得追溯修改。

### 4.2 月期间日比例

自然月期间 `[month_first, next_month_first)`。若资格区间只覆盖部分月份：

`eligible_fraction = eligible_calendar_days / calendar_days_in_month`。

按真实日历天数，二月自动处理闰年。全月比例为 1。只有 `specified_date`、月中暂停/恢复或选择按事件日停止时才产生部分月；`current_month/next_month/specified_month` 的正常首期为全月。

例：标准月折旧 190.00，8 月 16 日开始，8 月有 31 天；首月未舍入金额 `190 × 16/31 = 98.0645…`，确认 98.06。

### 4.3 使用寿命终点

- 月周期寿命终点为资格起点向后加 `useful_life_months` 的同日，采用半开区间。
- 月末日期采用日历安全加月规则（目标月无同日则取月末）。
- 部分首月会有对应的部分尾月；最终尾月用剩余 DB 校正。

以上例中，60 个月寿命的最后一个部分月只覆盖终点前日期，最后期取剩余可折旧金额，确保首尾合计恰好一个标准月且总额不越过残值。

## 5. 停止、暂停、恢复与处置

### 5.1 暂停与恢复

- `suspend` 从事件 `effective_date` 起停止计提（该日不计）。
- `resume` 从 `effective_date` 起恢复（该日计）。
- 同日先后事件必须由 Service 拒绝或归并为明确的最终区间；不能产生负天数。
- 暂停期间不消耗“有效使用月数”；预计寿命终点按暂停的实际日历天数顺延。
- 月中暂停/恢复按资格天数比例；多段资格区间的天数去重后相加。

例：30 天月份从 11 日起暂停，当月只有 1–10 日有资格，比例 `10/30`。

### 5.2 永久停止和处置

政策/Profile 必须保存 `stop_rule`：

- `event_date`：停止/处置日不计提，可能产生部分月；
- `next_month`：事件所在自然月仍按整月规则计提，自次月 1 日停止。V1 公司默认采用该规则，且必须可配置，不能写死。

永久停止或处置从对应结构化事件的 `effective_date` 起不再生成未来折旧。资产当前状态已经是 `disposed/sold/other_disposed`、Profile 当前状态已经是 stopped，都不能覆盖事件日期：`next_month` 规则下处置当月仍须完整计提并确认后才能锁定快照。处置确认时快照取处置事务可见、按业务期间已确认的实际折旧；草稿批次不进入快照。

若当月折旧已经确认，而后录入会影响该月的更早事件日期：

1. 系统不得静默改写已确认分录；
2. 财务先冲销受影响批次，再按事件重生成，或在有正式理由时做明确调整；
3. 处置确认不得制造“账面快照与确认折旧来源不一致”的状态。

## 6. 年限平均法 `straight_line`

### 6.1 月周期

初始完整月金额（未舍入）：

`monthly_raw = (C - S) / useful_life_months`。

当期未舍入金额：

`raw = monthly_raw × eligible_fraction`。

发生减值或估计变更后，从新 Profile 生效日按剩余 DB 和剩余有效月数前瞻重算：

`new_monthly_raw = DB_at_effective_date / remaining_useful_month_equivalents`。

不回改旧月份。

示例：原值 12,000.00，残值率 5%，60 个月，全月起算。残值 600.00，可折旧基础 11,400.00，每月 190.00，60 期累计 11,400.00，期末净值 600.00。

### 6.2 年周期

年周期用 `useful_life_years = useful_life_months / 12`；必须整除 12。完整年度金额 `(C-S)/useful_life_years`。部分年度按真实有资格天数/该折旧年度总天数计算，最后年度校正尾差。

## 7. 工作量法 `units_of_production`

初始单位折旧（不提前量化）：

`rate_per_unit = (C - S) / U_total`。

当期：

`raw = rate_per_unit × U_period`。

约束：

- `U_total>0`，工作量单位必填且整个 Profile 一致。
- 当期与累计工作量非负、不得倒退。
- 超过剩余预计工作量时，系统提示并将可计提工作量封顶；财务若确需变更预计总量，应先创建新 Profile 版本。
- 达到预计总工作量时，本期直接计提剩余 DB。
- 没有已确认当期工作量时批次标记 error，不能以 0 静默确认；财务明确“当期 0”后才可跳过。

示例：原值 10,500.00，残值 500.00，预计 100,000 小时，当期 8,000 小时。单位折旧 0.10，当期折旧 800.00。

## 8. 双倍余额递减法 `double_declining_balance`

双倍余额法初期不从基数中扣残值，但每期仍受 `BV>=S` 地板约束，并在适当期间切换直线法。

### 8.1 月周期

固定月折旧率：

`ddb_rate = 2 / useful_life_months`。

当期候选：

`ddb_raw = BV_before × ddb_rate × eligible_fraction`。

同时计算剩余直线候选：

`sl_raw = DB_before / remaining_useful_month_equivalents × eligible_fraction`。

当 `sl_raw >= ddb_raw` 时，从该期起锁定切换为直线法；后续不能因舍入波动切回双倍余额法。最终仍应用 DB 封顶和最后一期校正。

规范示例：原值 12,000.00，残值 600.00，60 个月，全月起算：

- 第 1 月：400.00，期末 BV 11,600.00；
- 第 2 月：386.67，期末 BV 11,213.33；
- 第 3 月：373.78，期末 BV 10,839.55；
- 第 36 月开始切换直线法，当月 122.53；
- 第 60 月计提剩余 122.53，期末 BV 600.00。

实现必须按逐期 Decimal 账面余额运行，不能用 float 闭式公式重建已确认历史。

### 8.2 年周期

`ddb_rate = 2 / useful_life_years`，其余切换和封顶相同。年周期要求 useful_life_months 可被 12 整除。

## 9. 年数总和法 `sum_of_years_digits`

V1 按会计年度折旧额计算，因此使用年限必须为 12 的整数倍：

`Y = useful_life_months / 12`，`denominator = Y × (Y + 1) / 2`。

第 `y` 个折旧年度（从 1 开始）的年度未舍入金额：

`annual_raw_y = (C - S) × (Y - y + 1) / denominator`。

- 年周期直接量化年度金额，最后年度校正。
- 月周期把该折旧年度金额分配到 12 个有效月；标准月未舍入额 `annual_raw_y/12`。
- 为避免每月舍入破坏年度目标，先量化该年度目标；前 11 个完整月正常量化，第 12 个完整月取“年度目标减本年已确认月额”。存在部分月/暂停时，按实际比例分配，并在该折旧年度最后有资格期间校正到年度目标，但不超过 DB。
- 折旧年度从资格起点起算，不因跨公历年重置；事件和部分月按第 4–5 节处理。

示例：原值 12,000.00，残值 600.00，5 年，年数和 15。第一年目标 3,800.00。月周期前 11 个完整月各 316.67，第 12 月为 316.63，全年合计 3,800.00。第二年目标 3,040.00。

## 10. 手工折旧与不计提

### 10.1 `manual`

- 每个应计期间必须由财务输入当期金额和原因，批次保存输入人及快照。
- 金额必须 `>=0` 且 `<=DB`；最后一笔可以等于剩余 DB。
- 空值是错误，不得自动当作 0；明确的 0 需要原因。
- 手工法仍通过批次确认并生成实际分录，不能直接编辑累计折旧。

### 10.2 `no_depreciation`

当期金额恒为 0，不创建普通折旧 Entry；批次可记录 skipped 原因。若从其他方法改为不计提，新 Profile 前瞻生效，历史保留。

## 11. 月度批次、确认与冲销

### 11.1 生成

- 一个 regular 月批次覆盖一个完整自然月和一家公司。
- `posting_period=monthly` 的资产每个自然月参与；`posting_period=yearly` 的资产只在 Profile 的 `annual_posting_month` 对应月参与，其余月为 skipped。机器值只能使用本规范第 1 节定义的 `monthly/yearly`。
- 生成时固定资产、Profile、事件、工作量、价值调整和公式版本都进入 BatchItem 快照。
- 相同 `idempotency_key + request_hash` 重试返回同一草稿；参数不同则冲突。
- 批次中任何应计资产为 error 时，整个批次不能确认。
- 月周期资产每月参与；年周期资产仅在 `annual_posting_month` 的月批次产生年度金额，其他月份记 skipped，不生成实际 Entry。

### 11.2 确认

确认在单个 PostgreSQL 事务中：

1. 锁定批次和所有相关 AssetFinance/Profile；
2. 重新验证期间未存在其他有效确认批次、输入快照未失效；
3. 对全部 ready item 创建来源唯一的 `DepreciationEntry`；
4. 逐资产验证残值地板、累计折旧和净值；
5. 将批次标为 confirmed，写确认人/时间和 AuditLog；
6. 全部提交或全部回滚，不允许“部分资产成功”。

confirmed 批次、item 和 entry 不可编辑或删除。

### 11.3 冲销和重算

- 冲销必须输入原因并创建一个 `batch_type=reversal` 的新批次。
- 每条反向 Entry 精确取原 Entry 金额的负数，并用 `reversal_of` 一对一关联；不重新计算公式。
- 反向批次确认后，原批次状态为 reversed，但原数据永久保留。
- 修正后重算创建更高 `generation_no` 的 regular 批次，以 `supersedes_batch` 指向原批次。
- 一个原批次只能有一个有效确认冲销。重复幂等请求返回既有冲销批次。
- 若后续月份依赖被冲销月份的期初余额，必须从最早受影响月份起按顺序冲销/重算，禁止只改中间月份造成断链。

## 12. 减值、处置和参数变更

### 12.1 减值

- 减值在生效日先减少 BV，再计算其后的折旧。
- 已确认历史不追溯变化；从下一未确认期间建立新 Profile 版本，以 `DB=max(BV_after_impairment-S,0)` 和剩余寿命前瞻计提。
- 减值转回不得使 BV 超过“假设从未发生该减值时”的账面价值，也不得产生负累计减值。
- 若减值生效期间已有确认批次，先冲销/重算或采用明确财务调整，不能直接改缓存。

### 12.2 处置

处置事务按 stop_rule 确定最后应计期间，使用已确认实际 AD 和 I 形成财务快照。处置收入不参与折旧公式。

对处置时仍为 active/suspended 的 Profile，完成处置必须新增结构化 `DepreciationProfileEvent(event_type=disposal_stop, source_disposal, previous_profile_status)`，stop effective_date 为：event_date 规则取实际处置日；next_month 规则取实际处置日次月 1 日。Profile 同事务置 stopped 以阻止新配置，但批次资格仍按 event effective_date 计算；next_month 下不得因当前 status 已 stopped 而漏掉仍应确认的处置当月。人工 stop、寿命 completed 和其他处置来源不得混用。

处置冲销只反向由该处置产生的 disposal_stop：新增一条 `event_type=disposal_restore`，以 `reverses_event` 一对一关联原 stop，source_disposal 相同，effective_date 与原 stop 完全相同，并把 Profile 恢复为 stop 保存的 active/suspended 原状态。原 stop/处置均保留。若 stop 后已有新 Profile、人工事件、冲突确认批次或其他后续业务，先阻断并列出冲突，不得猜测恢复状态。

恢复资格只重建未确认 Schedule/批次候选，不自动创建或改写实际 Entry。需要补记的未确认期间由后续批次处理；涉及已确认期间时按第 11 节先冲销/重算或做明确调整。

### 12.3 参数/估计变更

以下变更使用“克隆新 Profile 版本 + 原因 + 生效日”：方法、使用年限、残值、周期、起止规则、预计总工作量、工作量单位。

V1 普通估计变更只能在一个尚未确认自然月的首日生效；避免一个月内混用两套财务估计。暂停、恢复、处置等生命周期事件可按日生效。

已有确认历史时：

- 不回算、不覆盖；
- 新版的 opening BV/AD 来自生效日前已确认账面；
- 剩余寿命不得小于 1 个有效期间；
- 若用户要求追溯更正，必须先按顺序冲销受影响批次，再建立正确版本重算。

## 13. 实际与理论的展示/导出

页面和 Excel 必须明确列名，禁止只写“累计折旧”而混淆：

- `实际期初累计折旧`
- `本系统已确认折旧`
- `实际累计折旧`
- `实际账面净值`
- `理论累计折旧（测算，截至日期）`
- `理论与实际差额`

理论结果必须显示运行日期、参数版本和“仅供参考，不自动入账”。用户接受差额时仍需建立有权限、有原因、可冲销的调整来源。

## 14. 必测边界与验收

每种方法至少有正常、残值封顶、最后一期和冲销测试，并额外覆盖：

1. 0、0.005、负数冲销的 `ROUND_HALF_UP`；
2. 36 个月直线法 263.89 × 35 + 263.85 尾差示例；
3. 当前月、次月、指定月、指定日及闰年二月；
4. 月中暂停/恢复、多段区间和寿命顺延；
5. event_date 与 next_month 两种停止规则；
6. 工作量为 0、缺失、超预计总量和最后工作量；
7. 双倍余额第 36 月切换示例及永不切回；
8. 年数总和法年度目标与月度尾差示例；
9. 旧资产 opening 勾稽不等时拒绝，理论值不覆盖实际值；
10. 减值、减值转回和参数前瞻变更；
11. 月批次全有或全无确认、重复确认幂等、来源唯一；
12. 冲销金额精确相反、后续月份断链检测和重算链；
13. 处置前后折旧截止与财务快照一致；
14. Decimal 全链路测试，代码扫描/测试禁止财务公式使用 float；
15. PostgreSQL 唯一、CHECK、锁和并发确认测试，SQLite 不可替代。
