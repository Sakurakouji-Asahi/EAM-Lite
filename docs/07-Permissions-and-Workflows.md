# EAM-Lite 权限与工作流规范 V1.1

## 1. 适用范围

本文件是 V1.1 角色权限、数据范围、字段权限和受控状态转换的唯一详细规范。`docs/01-PRD.md` 定义产品口径，本文件决定“谁可以看、看哪些、可以做什么、在什么状态下做”。

所有规则必须在 Django 后端服务层、查询集、表单/API、导入、导出、扫码和附件下载中一致执行。只隐藏菜单、按钮或字段不构成权限控制。

权限采用“默认拒绝”：本文件未明确允许的动作一律禁止。V1.1 为单公司使用，但每条业务数据必须保存并校验 `company_id`，任何跨公司引用均拒绝。

## 2. 角色与组合规则

角色固定为：

| 角色 | 职责 |
|---|---|
| `system_admin` | 公司及系统配置、用户角色、基础资料、审计与备份；不是财务业务角色 |
| `finance` | 全公司资产财务认定、折旧、财务核对、盘点和处置财务数据 |
| `equipment` | 全公司资产实物主档、标签、调拨、盘点、设备保养和处置执行 |
| `department_manager` | 管理授权部门范围内的资产、部门盘点和人员/位置变动 |
| `employee` | 查看本人负责资产，执行被指派的盘点和保养 |
| `warehouse` | 全公司实物收管、初始化草稿、贴标、归还接收、位置流转和被指派盘点 |
| `hr` | 人员状态和离职资产清退，不修改资产财务数据 |
| `management` | 全公司实物和财务只读看板、明细与管理报表 |

一个用户可以拥有多个角色，一般动作按角色允许项取并集；但以下边界不得通过普通角色并集绕过：

1. 财务写字段只有 `finance` 可写。
2. `system_admin` 不自动获得财务字段查看或修改权；若同一人确需财务权限，必须另授 `finance`。
3. `management` 可以只读财务字段，但不能财务确认、确认折旧、导出 T+ 对账文件或修改业务记录。
4. 数据范围先求各角色允许范围的并集，再对每个对象执行公司边界和字段权限。
5. 临时越权、代操作、超级用户直改业务状态不属于业务功能；Django 超级用户也必须通过受控服务执行业务状态转换。

初始化引导存在一个受控的账号引导步骤：首次 Django superuser 只能创建首批应用用户并为其分配 `system_admin`、`hr`、`finance` 等固定角色，使对应业务角色能够完成后续初始化步骤。该引导不让 `system_admin` 自动继承 HR 或财务业务权限；同一自然人确需兼任时必须显式授予多个角色并留下审计记录。

首批 `system_admin` 已建立后，后续普通应用用户由 `system_admin` 通过受控用户页面创建。创建
必须验证当前操作人密码，只能选择固定角色，不得创建 staff、superuser 或自定义权限；用户、
初始部门范围、角色和审计在同一事务内提交。创建 `department_manager` 时必须同时配置至少
一个启用部门范围。

用户停用和角色变更必须防止系统失管：任何时候不得停用或移除最后一名可登录 `system_admin`，也不得在没有已确认替代人的情况下移除最后一名可登录 `finance`。高风险角色授予/撤销要求原因、近期身份确认和审计；不能通过直接编辑 Django Group 绕过 Service。

## 3. 数据范围

### 3.1 范围类型

| 范围 | 定义 |
|---|---|
| 公司全域 | 当前启用公司内的全部对象；不得跨公司 |
| 授权部门 | 用户被配置的一个或多个部门及明确勾选的下级部门；默认包含下级部门，不自动包含上级或同级部门 |
| 本人资产 | `responsible_employee_id` 为当前用户关联员工的非终态资产，以及其历史责任记录中的只读摘要 |
| 指派任务 | 当前用户被列为执行人的盘点任务快照行或保养计划/记录，仅在任务有效期间提供完成动作 |
| 清退范围 | HR 可查看当前公司人员及清退所需的非财务资产摘要、清退项目和证据 |

盘点的“指派”来自 `InventoryTaskAssignee`；保养的“指派”在 V1 精确表示当前用户绑定的 Employee 等于 `MaintenancePlan.responsible_employee_id`。V1 不存在第二套隐含保养指派表。department_manager 的“指派/范围”须满足计划责任人身份或矩阵明确的范围动作，具体完成 Service 每次仍按当前关系重新鉴权。

### 3.2 各角色默认范围

| 角色 | 资产/业务数据范围 | 人员范围 |
|---|---|---|
| `system_admin` | 公司全域的非财务数据和系统数据 | 公司全域 |
| `finance` | 公司全域 | 公司全域只读业务资料 |
| `equipment` | 公司全域非财务数据 | 公司全域只读 |
| `department_manager` | 授权部门当前资产及该范围创建的任务 | 授权部门只读 |
| `employee` | 本人资产 + 指派任务 | 本人 |
| `warehouse` | 公司全域非财务资产 | 公司全域只读 |
| `hr` | 清退范围 | 公司全域可维护任职状态 |
| `management` | 公司全域只读 | 公司全域只读 |

部门范围以资产当前 `department_id` 判断；历史记录仍可显示变动当时部门名称。部门经理执行调拨时，来源部门和目标部门都必须在其授权范围内；跨出或跨入授权范围的调拨只能由 `equipment` 或 `finance` 执行。

盘点执行人即使不是资产责任人，也可查看其被指派任务快照行所需的非财务字段，但任务权限不会扩展到资产总账其他记录。

## 4. 字段分组与查看权限

### 4.1 字段分组

| 分组 | 包含内容 |
|---|---|
| P0 识别摘要 | 正式编号/草稿号、名称、封面图、实物分类、状态、标签状态 |
| P1 实物资料 | 品牌、型号、厂家、序列号、出厂编号、历史编号、单位、部门、责任人、位置、购置/启用日期、保养属性、非财务备注、实物变动历史 |
| F1 财务资料 | 会计认定、固定资产类别、原值、资本化日期、折旧配置、残值、累计折旧、减值、净值、财务调整、理论/实际折旧、T+ 外部卡片号、处置财务快照及收入 |
| A0 普通附件 | 资产照片、说明书、合格证、盘点照片、保养附件、普通清退证据 |
| A1 财务附件 | 发票、合同、验收单、出售凭证及标记为财务敏感的其他附件 |
| S0 安全系统数据 | 用户角色、权限分配、审计日志、备份、配置密钥状态（永不显示密钥值） |

`范围内` 表示仍受第 3 节数据范围限制；“摘要”仅含 P0 及部门、责任人、位置、状态。

| `equipment` | 公司全域查看 | 不可见 | 公司全域查看 | 不可见 | 不可见 |
| `department_manager` | 授权部门查看 | 不可见 | 授权部门查看 | 不可见 | 不可见 |
| `employee` | 本人资产/指派任务查看 | 不可见 | 本人资产及指派任务查看 | 不可见 | 不可见 |
| `warehouse` | 公司全域查看 | 不可见 | 公司全域查看 | 不可见 | 不可见 |
| `hr` | 公司全域摘要 | 不可见 | 仅清退相关查看 | 不可见 | 仅审计：人员/清退对象及本人 HR 动作 |

| 步骤 | 状态转换 | 执行角色 | 后端原子操作与校验 |
|---|---|---|---|
| 保存草稿 | 新建/保持 `draft` | finance/equipment/warehouse/范围内 dept mgr | 公司边界；数量强制为 1；不生成正式编号或 Token |
| 提交 | `draft → pending_finance` | 同上 | 名称、实物分类、单位、部门、责任人、位置、至少一张资产照片完整 |
| 撤回/退回更正 | `pending_finance → draft` | 原提交人可撤回；finance 可退回 | 必须记录原因；不产生编号 |
| 财务确认 | `pending_finance → pending_label` | finance | 所有会计认定均须有不小于 0 的原值；累计折旧和减值可明确为 0；固定资产另须固定资产类别及折旧资料完整；同一事务发放永久编号、创建二维码身份、写审计日志 |
| 打印 | 标签 `ready_to_print → printed` | finance/equipment/warehouse | 点击打印并生成 A4 预览时在同一事务记录批次、操作人和时间；不设置独立确认打印步骤 |
| 贴标启用 | `pending_label → in_use/idle`，标签 `printed → attached` | finance/equipment/warehouse | 扫描当前 Token，或在受权限保护的 Web 资产页查看当前二维码并逐项勾选确认；再次校验当前 active 身份、printed 状态、责任人/部门/位置；同一事务更新状态并记录确认方式和审计 |

财务确认只是财务角色直接确认会计处理和资料完整性的业务动作，不是审批。V1.1 不实现审批定义、审批实例、审批节点、会签、抄送、审批意见或钉钉接口。

正式编号一经发放永不回收。财务确认事务失败时，资产状态、编号登记、计数器、二维码身份和审计记录必须全部回滚。

### 6.2 换标

- 未贴标前的打印重试沿用当前 Token，新增打印批次记录。
- 已贴标后选择“换标”，填写原因并在同一事务吊销旧 Token、创建新 Token、把标签状态改为 `ready_to_print`。
- 资产业务状态不改变；旧 Token 永久返回“标签已失效”，不跳转到资产详情。
- 新标签再次经过打印，并通过扫码或 Web 逐项确认。待办“待贴二维码”包含此类在用但等待换标的资产。

## 7. 正式资产变动工作流

### 7.1 部门、责任人和位置

正式资产编辑页不得直接修改三项当前值。变动动作必须收集新值、生效日期、原因和备注，在单一事务中：

1. 校验角色、公司和部门范围；
2. 写入不可删除的 `AssetMovement`；
3. 更新资产当前值；
4. 写审计日志。

三项可以在同一调拨动作中同时变化。新责任人必须属于当前公司，且统一满足 `employment_status='active' AND is_active=true`；`leaving`、`resigned` 或已停用员工不得通过领用、调拨、责任人变更或任何批量/API 入口接收新资产。目标位置和目标部门必须属于当前公司。

### 7.2 借出与归还

- 借出仅允许在用或闲置资产，先选择借用方类型并保存借出前状态。
- `borrower_type=internal_employee` 时必须填写结构化 `borrower_employee` 关联，并令外部输入 `borrower_name`、`borrower_organization` 为空；服务端保存不可编辑 `borrower_name_snapshot`。员工必须属于当前公司且满足 `employment_status='active' AND is_active=true`，姓名/单位文本不得代替员工关联。`leaving`、`resigned` 或已停用员工不得成为新的内部借用人。
- `borrower_type=external` 时必须令 `borrower_employee` 为空，`borrower_name` 必填、`borrower_organization` 可空；只有外部类型允许手填姓名和单位。内部与外部字段必须互斥，后端拒绝同时填写或两边都未填写。
- 两种类型都必须填写借出日期、预计归还日、经办人和原因。上述信息保存为结构化 `AssetLoan`，并与借出/归还的 `AssetMovement` 关联，不得只拼进备注或审计文本。
- 归还填写实际归还日、接收人和实际位置，先恢复借出前状态；如归还同时改变部门/责任人/位置，或另行在 `in_use/idle` 间变化，在同一受控动作生成对应变动记录。
- 借出资产不能直接处置，必须先归还。

### 7.3 闲置、启用和维修占用

- `in_use ↔ idle` 必须填写生效日和原因。
- `in_use/idle → under_repair` 保存送修前状态；维修完成恢复原状态并记录结果。
- V1.1 维修状态仅保留占用历史，不创建维修工单或维修费用模块。

## 8. 盘点工作流

1. **草稿**：有权角色选择类型、范围、计划日期和执行人。
2. **发布**：在同一事务生成不可变应盘快照并进入 `in_progress`；快照保存当时编号、名称、部门、责任人、位置和状态显示值。
3. **执行**：执行人只能扫描指派任务。位置、责任人、状态逐维比较；两个以上维度不一致保存为 `multiple_mismatch` 并保留全部现场值。系统内但不在快照的资产记为“非本任务资产”；未知实物建立无 `asset_id` 的盘盈记录并强制上传照片。
4. **停止扫码**：有权角色进入 `reconciliation`；未扫描行标为未盘，不再接受普通扫描。finance/equipment/范围内 department_manager 可在差异工作台对单一未盘行执行“受控补盘”：重新扫描当前 QR、填写原因并新增 supplemental Scan，任务不退回执行中；普通 Assignee 无此权限。
5. **处理差异**：每项异常选择主档变动、主档无误、盘亏处理或其他明确结论。主档变动必须调用正式资产变动服务，不能由盘点结果直接覆盖。
6. **处理盘盈**：只有 finance 可将盘盈转草稿；也可标记非公司资产、重复或其他并填写说明。
7. **关闭**：所有异常/未盘快照行及所有盘盈均有处理结论后才允许关闭；正常行以有效扫描结果为证据，不创建虚假结论。财务全盘只由 finance 关闭；部门/专项任务按矩阵关闭。

关闭后禁止编辑扫描和结论。纠错创建关联原记录的更正记录；取消已发布任务必须填写原因且不删除快照及已有扫描。

## 9. 保养工作流

1. equipment 建立启用计划；周期单位仅日、周、月、年。
2. 系统按计划计算即将到期和逾期，不创建审批任务。
3. 责任人、equipment 或被指派执行人建立完成记录并确认；确认后记录不可编辑。
4. 结果为发现问题时，问题说明必填并生成 `open` 跟进项。
5. equipment 或范围内 department_manager 填写处理说明，将跟进项置为 `closed`。
6. 错误完成记录只能作废并重建；作废不删除历史，且重新计算最近完成日和下次到期日。
7. 资产进入处置终态时，系统终止其启用/暂停计划。

## 10. 离职资产清退工作流

| 步骤 | 执行角色 | 规则 |
|---|---|---|
| 发起 | hr | 员工从 `employment_status=active` 改为 `leaving` 并明确置 `is_active=false` 时自动创建清退单，快照发起时当前负责的所有非终态资产和以 `borrower_employee` 关联的未归还内部借用资产 |
| 禁止新增关联 | 系统 | 员工进入 `leaving` 后，所有新领用、转交、调拨和内部借用在候选查询与动作服务两层拒绝；未完成清退单不能绕过此规则 |
| 活动单刷新 | hr/系统 | HR 可手工触发，系统可在既有关联状态变化后调用同一 Service；只补入关联生效时间不晚于清退发起时间、但发起后才被发现，或因既有关联资产状态变化而变为应清退的资产；记录原关联生效时间、发现时间和原因，不接受清退发起后的新关联 |
| 归还 | equipment/finance/dept mgr/warehouse 接收 | 必须指定接收部门、责任人、位置和归还后状态，生成变动记录 |
| 转交 | equipment/finance/范围内 dept mgr | 必须完成正式责任/部门/位置变动后，清退项才解决 |
| 处置 | equipment/finance | 清退项保持“处置中”，直到关联处置记录进入终态 |
| 完成首次清退 | hr | 仅未处理数为 0；HR 明确填写不早于入职日、不晚于当前上海业务日的 termination_date，同事务关闭并把人员改为 `resigned` |
| 建立/完成补充清退 | hr | 已完成后发现遗漏时带原因新建指向原单的补充清退，原单不重开；员工保持 resigned 和原 termination_date，补充单解决后只关闭新单 |

HR 只能发起、刷新/补充、查看和完成已清零的清退，不能替代实物角色执行归还/转交，不能把未处理项强制清零。后端必须阻止存在未处理资产时将员工直接改为已离职，也必须阻止向 `leaving` 员工建立任何新资产关联。处置 confirmed 的终态 Item 视为不再承担活动责任，即使 Asset 保留最后责任字段用于历史显示。

## 11. 处置工作流

1. finance、equipment 或范围内 department_manager 发起处置，填写申请日期和拟处置日期 `planned_disposal_date`，资产进入 `pending_disposal` 并保存原状态；发起时实际完成日期 `actual_disposal_date` 为空，拟处置日期只用于计划和提醒。
2. 实物处置发生后，具备完成权限的 finance 或 equipment 填写实际完成日期 `actual_disposal_date`；该日期不得早于申请日期、不得晚于当前上海业务日。
3. finance 只能以实际完成日期为截止日从权威财务数据生成并锁定原值、累计折旧、减值、净值和收入；实际完成日期为空时禁止锁定，非财务角色只看到“已核对/未核对”。
4. finance 或 equipment 上传相应证据并执行完成；equipment 完成前必须存在已锁定财务快照，完成动作复用锁定时的实际完成日期，不得使用拟处置日期。
5. 按类型进入 `disposed`、`sold` 或 `other_disposed`；终态生效日及折旧截止口径使用实际完成日期，并终止保养。
6. 财务锁定后实际完成日期和快照不可直接修改；发现日期错误时，未完成处置只能带原因取消并重新发起，原 Disposal、快照和附件继续保留。
7. 未完成前可由 finance/equipment 带原因取消，把原 Disposal 标为 `cancelled` 并恢复原状态。
8. 终态错误仅 finance 可建立一对一 `AssetDisposalReversal`：必须填写原因、确认不存在后续业务记录，把原 Disposal 标为 `reversed` 并恢复处置前状态；终态保留的最后责任人若已非 active，须同时指定合法替代责任人并写 Movement，否则阻断；原处置、财务快照、附件和冲销均保留。

V1.1 不创建通用处置审批流。“财务锁定快照”和“实物完成处置”是职责分离的业务步骤，不是审批节点。

## 12. 附件权限

附件访问权限取决于“关联业务对象权限 + 附件字段组权限”，两项都通过才允许查看或下载。

- 未正式化资产照片可以挂在草稿；盘盈照片直接挂在盘盈记录，不伪造资产。
- 保养、盘点、处置、清退附件分别挂其业务对象并沿用该对象数据范围。
- A1 财务附件仅 finance、management 可查看；management 只读。
- 已提交或正式业务附件不得物理删除；有权编辑该业务对象的角色只能执行“作废”，填写原因并保留文件元数据和审计。
- 临时下载 URL 必须短时有效且再次校验登录；禁止可枚举的公开文件路径。

## 13. 后端实现与测试要求

### 13.1 强制实现

1. 所有对象查询先限制当前公司，再应用角色数据范围。
2. 详情和动作端点重新查询授权对象，不信任前端提交的隐藏字段或对象 ID。
3. 财务字段使用独立表单/序列化字段白名单；无权角色的请求即使提交财务字段也必须报错且不保存。
4. 状态字段不允许普通 `update()` 或模型表单直接写，全部通过受控服务函数和数据库事务。
5. 导入逐行检查公司、部门和字段权限；导出复用同一授权查询服务。
6. 扫码先验证 Token，再验证用户对资产或指派任务的权限；二者任一失败均不返回敏感资料。扫码或单资产 Web 贴标的不透明来源兼容只接受 `QR_BASE_URL` 或无通配符 `CSRF_TRUSTED_ORIGINS` 中的精确 Host，并只允许在标准 CSRF Token 已验证后进入同一贴标 Service。Web 确认必须验证服务器生成、绑定当前登录会话与精确 POST 路径的短时签名桥接令牌；扫码确认优先验证该桥，兼容旧页面时必须以恒定时间比较扫描 URL Token 与隐藏表单 Token。不得绕过登录、角色、公司/部门范围、当前二维码或打印状态。
7. 所有拒绝、关键成功动作和权限配置变更写审计日志；日志不得包含密码、Token 原文或密钥。

### 13.2 最低自动测试

必须覆盖：

- 每个角色对每个字段分组的允许与拒绝；
- 部门经理跨部门、员工查看他人资产、执行人访问非指派任务的拒绝；
- system_admin 无 finance 角色时无法读取或修改 F1/A1；
- management 只读且不能导出 T+；
- UI 隐藏与直接构造 HTTP 请求得到相同拒绝结果；
- 列表、详情、扫码、附件、导入、通用导出、T+ 导出的范围一致；
- 所有合法和非法状态转换；
- 事务失败时状态、历史、编号、Token 和审计的一致回滚；
- 离职未清阻断、盘点未闭环阻断、处置未锁财务快照阻断；
- 正式资产 `quantity = 1`，任何其他数量均被拒绝。
