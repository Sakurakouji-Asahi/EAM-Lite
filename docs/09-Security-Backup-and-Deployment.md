# Security, Backup and Deployment Specification V1.1

本文件定义 EAM-Lite V1 在公司局域网中的最低安全、部署、备份和恢复要求。局域网不是可信边界；HTTPS、后端权限、备份隔离和恢复演练都不能因“只连公司 Wi-Fi”而省略。

## 1. V1 生产架构

推荐单机应用 + 独立备份目标，保持 Django 单体架构：

```text
PC/手机浏览器（公司 LAN）
        │ HTTPS 443
        ▼
反向代理（Nginx 或 Caddy，内网证书）
        │ loopback/Unix socket
        ▼
Gunicorn/WSGI → Django Templates + HTMX
        │
        ├── PostgreSQL（仅本机/受限管理网）
        └── 受保护附件目录（不公开直链）

夜间备份 → 另一物理设备/NAS + 定期离线加密副本
```

保持：Python、受支持的 Django 稳定版、PostgreSQL、Bootstrap、HTMX、Django Templates。V1 不引入 React/Vue、微服务、Redis、Celery、公共对象存储或外网 API 依赖。

生产进程不得使用 `manage.py runserver`。可选择 systemd + Python virtualenv，或受控的 Docker Compose；项目只能选一种并在 README/运维手册固定精确版本、目录、服务名和命令。无论哪种方式，数据库与附件均不得因重新部署容器而丢失。

## 2. 网络与 LAN HTTPS

### 2.1 网络边界

- 生产主机使用固定内网地址和内部 DNS 名称，例如 `eam.company.lan`；浏览器只访问该名称。
- 边界防火墙/主机防火墙只允许授权公司 LAN 网段访问 TCP 443；HTTP 80 仅用于跳转 HTTPS，或完全关闭。
- PostgreSQL 5432 不向普通 Wi-Fi 客户端开放。优先仅监听 loopback/Unix socket；确需管理访问时仅放行指定管理主机和独立数据库账号。
- Gunicorn 只监听 loopback 或 Unix socket，不直接暴露到 LAN。
- 禁止路由器端口映射、UPnP 公网暴露和临时公网隧道。远程访问属于 V1 范围外，必须另行安全评审。
- `ALLOWED_HOSTS` 仅列实际内网域名；`CSRF_TRUSTED_ORIGINS` 仅列准确的 `https://` 来源，不使用 `*`。

### 2.2 TLS

- 即使在 LAN 内也必须 HTTPS。使用公司内部 CA 签发证书，并把 CA 根证书通过受控方式安装到公司终端；或使用组织认可的可验证证书方案。
- 私钥权限仅服务账号可读，不进入 Git、镜像、压缩包、日志或数据库备份下载包。
- 只启用 TLS 1.2/1.3 和现代密码套件；证书到期至少提前 30 天告警。
- HTTP 请求永久/临时重定向到 HTTPS；验证所有支持终端不会出现证书警告后再启用合理 HSTS。内部证书未部署完成前不得用“点击继续”作为上线方案。
- Django 正确设置代理头，只信任本机反向代理；开启 `SECURE_SSL_REDIRECT`、`SESSION_COOKIE_SECURE`、`CSRF_COOKIE_SECURE`。

## 3. 业务区域、语言和时间

- `LANGUAGE_CODE = zh-hans`。
- `TIME_ZONE = Asia/Shanghai`，`USE_TZ = True`；数据库时间戳存 UTC，页面、Excel 和业务日期按上海时区转换。
- 服务器操作系统也建议设置 NTP 同步和明确时区，但业务逻辑不得依赖服务器默认时区。
- 默认币种 CNY，金额 `Decimal`。Excel 金额输出为数值单元格并带人民币/两位小数格式，不输出为文本。
- 日/月边界、编码年月、折旧期间、盘点时间和备份日期均以明确的上海业务日定义；日志保留带时区 ISO 8601 时间。

## 4. 本地静态资源与离线能力

- Bootstrap、HTMX、图标、字体、二维码生成库的前端资源必须固定版本并随项目放在 `static/vendor/` 或构建产物中。
- 模板不得引用公共 CDN、Google Fonts、远程分析脚本、公共 JavaScript、远程图片占位或在线二维码服务。
- 依赖下载只发生在受控构建/安装阶段；生产页面运行不依赖互联网。
- 使用 Django `collectstatic` 生成只读静态目录，由反向代理以带内容哈希的缓存策略提供。
- 设置 Content Security Policy：默认只允许 self；不使用 `unsafe-eval`。如 HTMX/内联样式需要例外，应最小化、记录并测试。
- 第三方许可证和实际锁定版本进入仓库；升级前做回归与安全检查。

验收时断开公共互联网，登录、查询、二维码扫描、A4 标签预览、盘点、保养和 Excel 导入导出仍须正常工作。

## 5. 配置与 Secret

所有环境差异从环境变量或权限受控的外部配置读取。至少包括：

- `SECRET_KEY`
- 严格布尔 `DEBUG`
- 数据库 name/user/password/host/port
- `ALLOWED_HOSTS`、`CSRF_TRUSTED_ORIGINS`
- 静态、附件、临时上传和备份目录
- 日志级别
- TLS/代理相关开关
- 备份加密密钥的引用位置（不是密钥原文）

要求：

- `.env`、证书私钥、数据库密码、备份口令、QR Token、会话 Cookie 不进 Git。
- `.env.example` 只放占位符和说明。
- 生产 `DEBUG=False`；配置缺失时启动失败，不静默使用开发默认值或 SQLite。
- Secret 以服务账号最小文件权限或组织认可的 Secret 机制提供；人员变更、疑似泄露或恢复到新主机后轮换。
- 日志、异常页面和 AuditLog 对密码、Secret、Token、Cookie、Authorization、完整请求体进行过滤。

## 6. 身份、会话与权限

- 使用 Django 可靠密码哈希器和自定义 User；绝不保存可逆密码。
- 首次管理员密码通过安全的本机/管理终端创建，不写在文档或脚本中；上线后禁用共享账号。
- 连续失败登录进行速率限制和安全日志记录，但错误提示不泄露账号是否存在。
- 停用用户立即拒绝新登录；高风险离职场景由管理员清理现有会话。
- 退出必须 POST + CSRF 防护。所有改变状态的请求均需 CSRF，GET 必须只读。
- Session Cookie 至少 `Secure`、`HttpOnly`、`SameSite=Lax`；合理设置空闲过期和绝对过期。财务/管理员在共享终端使用后必须退出。
- 角色、字段权限、公司/部门数据范围全部在后端查询和 Service 再校验，默认拒绝；规则见 `docs/07-Permissions-and-Workflows.md`。
- Django superuser 仅用于恢复，不替代正常角色。使用 superuser 的关键操作同样写审计。
- 对正式发号、财务确认、折旧确认/冲销、处置、备份下载等高风险 POST 使用幂等键并再次校验当前权限。

## 7. 应用与数据库安全

- 所有数据库访问使用 ORM 参数化查询；少量必要原生 SQL 必须参数绑定、代码评审和测试。
- 数据库应用账号不使用 PostgreSQL superuser，不拥有创建角色/数据库权限；迁移账号可单独管理。
- 生产应用账号不得 DELETE 已发编号、折旧分录、处置、正式资产和 AuditLog。
- 对编码、折旧确认、处置、盘点快照等使用数据库事务、行锁、唯一/CHECK/constraint trigger；不能只靠表单校验。
- HTML 默认转义用户内容；禁止把备注直接标记 safe。富文本不在 V1 范围。
- 设置安全响应头：`X-Content-Type-Options: nosniff`、合理的 frame policy、Referrer-Policy、CSP。
- 错误页对用户显示 correlation ID，不显示堆栈、SQL、文件路径或配置；详细信息仅进入受限运行日志。
- 依赖使用精确 lock 文件；上线前检查已知高危漏洞。无法联网的生产机由构建环境完成扫描并保存报告。

## 8. 二维码与附件安全

### 8.1 二维码

- 二维码只包含 HTTPS 应用 URL + 至少 128 bit CSPRNG 随机 Token，不包含资产名称、原值、责任人、部门或连续主键。
- 数据库保存可重印标签所需的高熵 `public_token`。该值印在实物标签上，因此只作为不可猜测的公开标识，不作为授权凭据；扫描后仍需登录并执行对象权限检查。数据库备份和管理页面仍须保护该字段。
- 换标时轮换 Token，旧 Token 标记 revoked 并永久失效；不得因编号不变继续沿用已泄露 Token。
- 应用日志和 AuditLog 不记录完整 Token；必要时只记录不可用于访问的截断摘要。

### 8.2 上传

- 附件位于静态目录和 Web root 之外；下载必须经过 Django 权限校验，再由受控流式响应或反向代理内部跳转提供。
- 文件名由服务器生成随机 `storage_key`；原文件名仅作显示并进行转义，禁止 `../`、绝对路径、NUL 和双扩展欺骗。
- 同时校验允许扩展名、MIME、文件签名和大小。V1 白名单/上限由管理员配置并在 README 给出；宏启用 Excel 默认拒绝。
- 图片解码时限制像素和资源消耗；Office/PDF 不在服务器执行宏、脚本、外部链接或嵌入对象。
- 保存 SHA-256、大小和扫描状态。组织有恶意软件扫描能力时在可下载前隔离扫描；没有扫描器时至少白名单、签名校验并标记策略限制。
- 下载响应使用安全 `Content-Disposition` 和 `nosniff`；危险类型只允许 attachment，不内联。
- 附件删除只针对无业务关联且超过保留期的孤儿文件，由有审计的清理任务执行。

### 8.3 导入暂存与证据保留

- `confirmed` 导入批次、行级规范化/错误结果、创建对象映射、原文件 Attachment 和摘要属于建档证据，V1 不提供普通删除；随相关业务记录和备份策略保留。
- `uploaded/invalid/failed` 且从未创建业务对象的批次默认保留 30 天，便于用户修正和安全调查；组织可延长但不能设置为 0。`validated` 待确认批次不由定时任务自动删除，必须先由有权用户明确放弃并留下审计，V1 不另造 `cancelled` 状态。
- 清理任务先锁定 Batch，再重新确认状态不是 confirmed、所有 Row 均无 created 对象映射、没有相关幂等请求仍在处理，并记录批次 ID、摘要、清理人/任务和时间；任一条件不满足即跳过。删除 Batch/Rows 后，原文件只进入孤儿候选，经过附件孤儿保留期和再次引用检查才可删除底层对象。
- 临时解析副本只放 `/var/lib/eam-lite/tmp/` 的随机受限目录，请求完成或失败后尽快清理；服务重启后的定时清理只能处理超过明确时限且不属于活动任务的临时文件，不能把临时目录当导入证据存储。

## 9. 日志、审计与监控

运行日志和业务 AuditLog 分离：

- 运行日志：启动、请求错误、数据库/磁盘/备份故障，用于诊断。
- AuditLog：谁在何时对哪个业务对象做了什么，含脱敏 old/new 快照。

最低要求：

- 关键业务和强审计记录在同一事务提交；审计失败则业务失败。
- 日志滚动、限制磁盘占用；普通应用用户无权修改日志。
- 监控服务可用性、5xx、数据库连接、磁盘剩余、附件目录、备份结果、证书到期和系统时钟。
- 磁盘/备份剩余空间低于阈值时主动告警；不得等到备份写满生产盘。
- 每日检查最后一次成功备份的时间和大小异常。只看到“命令退出 0”不等于备份可恢复。
- 时间同步失败、连续登录失败和异常批量导出应进入安全日志并供管理员查看。

## 10. 生产目录与权限

实际路径可调整，但必须分离：

```text
/opt/eam-lite/app/             只读发布代码
/etc/eam-lite/                 环境配置与证书引用，受限
/var/lib/eam-lite/media/       受保护附件
/var/lib/eam-lite/tmp/         临时上传，定期清理
/var/log/eam-lite/             运行日志
/var/backups/eam-lite/stage/   本机短暂备份暂存，不是唯一备份
```

- 应用使用专用无登录系统账号；代码/配置/附件/备份目录按最小权限分开。
- 反向代理不能列目录；应用账号不能读取 TLS 私钥以外不必要的系统文件。
- PostgreSQL 数据目录由数据库服务账号独占。
- 本机备份暂存必须在复制并校验到独立目标后清理，不能与生产数据共处成为唯一副本。

## 11. 发布、迁移与回滚

### 11.1 上线前

1. 在类生产 PostgreSQL 环境运行全部测试、迁移和静态检查。
2. 检查工作树/发布包、精确依赖锁、变更说明和迁移计划。
3. 生成上线前数据库 + 附件一致性备份并校验 manifest。
4. 执行 `manage.py check --deploy` 或当时 Django 等效检查，逐项处理而不是忽略。
5. 确认 `DEBUG=False`、允许主机、HTTPS、邮件/告警（如启用）、磁盘和备份目标。
6. 对可能锁表/长耗时迁移在副本数据上测时，安排维护窗口。

### 11.2 发布

- 使用版本化发布目录或不可变镜像；不得在生产目录手工编辑 Python 文件。
- 顺序：进入维护窗口（如需）→ 最终备份 → 迁移 → collectstatic → 重启应用 → 健康检查 → 业务冒烟 → 退出维护。
- 健康检查至少验证反向代理、Django、数据库和只读存储状态，但不泄露版本/Secret。
- 冒烟包括登录、资产查询、权限隔离、本地静态资源、受保护附件和一个只读报表。

### 11.3 回滚

- 代码回滚不能盲目反向执行破坏性迁移。每次发布说明数据库迁移是否向后兼容及恢复路径。
- 优先采用 expand → migrate data → contract 的兼容迁移。
- 若必须恢复数据，按第 13 节在隔离环境验证备份后执行，明确会丢失 RPO 窗口内的变更并由业务负责人确认。
- 禁止用 `git reset --hard`、删除数据目录或直接覆盖生产数据库作为标准回滚。

## 12. 备份目标与保留

### 12.1 目标

- RPO（可接受最大数据丢失）：不超过 24 小时。
- RTO（从批准恢复到核心登录、资产查询和附件可用）：不超过 4 小时。
- 每日自动备份 PostgreSQL 和附件，最近 30 个成功日备份可恢复。
- 系统管理员可生成/下载一次受保护的手动备份，但浏览器下载不是自动备份的替代。

若业务认为 24 小时数据丢失不可接受，应在上线前提升为更频繁备份或 PostgreSQL WAL 归档；不能在事故后声称已有更小 RPO。启用 PITR 时须另写、测试保留和恢复步骤。

### 12.2 备份集

每个备份集包含：

1. PostgreSQL `pg_dump` custom 格式（或经批准的物理/PITR 方案）；
2. 附件目录快照/归档；
3. manifest：备份集 ID、应用版本、数据库版本、schema migration 列表、开始/结束时间、业务时区、文件数量/总大小、各文件 SHA-256；
4. 加密说明和恢复说明版本；
5. 不包含明文 `.env`、TLS 私钥和备份解密密钥。

数据库与附件需要一致性窗口。小规模 V1 可在短暂维护/上传冻结窗口内：记录水位 → dump 数据库 → 快照附件 → 记录完成水位；manifest 标明范围。不得把随机时点的数据库 dump 和旧附件压缩包拼为同一“成功”备份。

### 12.3 3-2-1 与加密

- 至少保留生产数据 + 独立 NAS/备份设备副本 + 定期离线/离机加密副本；同一主机另一目录不算独立备份。
- 备份传输和静态存储均加密；密钥与备份分离，至少两名授权人员可按流程恢复，避免单点人员风险。
- 备份目标账号只授予写入指定目录和必要读取验证权限；生产应用账号不得删除历史备份。
- 每日任务先写临时名，完成校验后原子标记 `SUCCESS`；失败/不完整集不参与 30 天轮换。
- 轮换只删除超过保留期且存在足够成功副本的明确备份集，并记录日志；不得用宽泛未校验路径执行递归删除。

### 12.4 自动校验

每日备份完成必须自动检查：

- 命令退出码；
- dump 可列目录/格式有效；
- 附件数量和大小与 manifest 相符；
- SHA-256；
- 目标可读且剩余空间足够；
- 最近成功备份未超过 24 小时。

校验失败立即告警且不把该日标为成功。单纯存在一个非空压缩包不算验证。

## 13. 恢复流程与演练

### 13.1 恢复步骤

恢复必须先在隔离网络/新数据库执行，禁止直接覆盖唯一生产实例：

1. 记录事故时间、期望恢复点、批准人和预计数据丢失窗口。
2. 选择不晚于目标点的最近成功备份，验证 manifest、哈希、密钥和介质可读。
3. 准备匹配的 PostgreSQL/应用版本和空数据库；恢复角色/权限，不使用生产 superuser 运行应用。
4. 使用 `pg_restore` 恢复，运行 migration 状态检查；不得在未知 schema 上强行 migrate。
5. 恢复附件到新目录并验证 SHA-256、数量、权限和 Attachment 数据库引用。
6. 启动匹配版本应用，执行恢复验收清单。
7. 验收通过后再切换内网 DNS/服务指向；旧实例只读保留，避免覆盖证据。
8. 轮换恢复环境 Secret/会话，记录实际 RPO/RTO、缺失数据和后续补录计划。

### 13.2 恢复验收

至少抽查：

- 管理员和普通角色登录/权限；
- 公司、部门、员工、资产数量及关键状态；
- 已发代码历史和计数器不倒退；
- 最近两个折旧批次、实际累计折旧和净值勾稽；
- 随机至少 10 个附件可按权限打开，未授权访问被拒绝；
- QR 当前 Token 有效、已撤销 Token 无效；
- 盘点快照、保养记录、处置快照和 AuditLog；
- 新建草稿和一个不正式占号的预览操作正常。

### 13.3 演练频率

- 首次生产上线前必须完成一次全量恢复演练并达到 RTO。
- 上线后至少每季度恢复到隔离环境一次；每次数据库大版本、备份脚本、存储位置或加密方式变更后额外演练。
- 演练报告记录备份集、开始/结束时间、实际 RPO/RTO、校验项、问题和整改责任人/期限。
- 未做恢复演练的备份只能称“已生成”，不能称“已验证可恢复”。

## 14. 管理员手动备份下载

- 仅 `system_admin` 可发起，需重新确认身份/近期登录，并记录 AuditLog。
- 后端生成带唯一 ID、有效期和状态的备份任务；同一幂等键不重复生成。
- 下载必须走鉴权响应，使用短时一次性授权；不能放在可猜测的 public/media URL。
- 下载包加密，口令/密钥通过与文件不同的受控渠道交付；过期后从暂存区安全清理。
- 日志记录发起人、时间、备份集、大小、成功/失败和下载完成，不记录解密密钥。
- 手动下载不得包含 TLS 私钥、`.env` 或明文 Secret，也不得延长/破坏自动备份的 30 天轮换。

## 15. 上线安全验收清单

全部通过才可上线：

- [ ] 内网 DNS 和受信任 HTTPS 正常，HTTP/直连 Gunicorn/5432 被阻止。
- [ ] `DEBUG=False`，Secret 不在仓库/日志，生产不回退 SQLite。
- [ ] 上海时区、CNY、NTP 和日/月边界测试通过。
- [ ] 断开互联网后本地 Bootstrap/HTMX/图标/二维码仍正常，无公共 CDN 请求。
- [ ] 八类角色、公司和部门数据范围、财务字段、附件下载均做后端拒绝测试。
- [ ] CSRF、Secure/HttpOnly Cookie、安全退出、停用用户和登录失败限制通过。
- [ ] QR 不含敏感字段，public Token 高熵且唯一、完整值不进入日志，撤销/换标测试通过。
- [ ] 上传白名单、大小、路径穿越、公式/宏文件和未授权下载测试通过。
- [ ] PostgreSQL 约束、并发发号、折旧确认/冲销和审计原子性通过。
- [ ] 每日数据库+附件备份、30 日保留、异机加密副本和失败告警已实际运行。
- [ ] 用最近备份完成隔离恢复，抽查通过，实测 RPO≤24h、RTO≤4h。
- [ ] 发布、回滚、恢复命令和负责人写入运维手册，另一名人员能够照文档执行。
