# EAM-Lite 企业资产管理系统 PRD V1.1

## 1. 文档定位与优先级

本文件是 EAM-Lite V1.1 的产品范围与验收口径。业务实现必须同时遵守：

2. 本文件：产品范围、业务流程与状态口径。
3. `docs/02-Business-Rules.md`：计算及数据处理规则。
4. `docs/03-Asset-Coding-Rules.md`：正式编号规则。
5. `docs/04-Database-Design.md`：数据模型与约束。
6. `docs/05-UI-UX.md`：页面与交互。
7. `docs/07-Permissions-and-Workflows.md`：角色、数据范围、字段权限及工作流。
8. `docs/11-Tplus-Reconciliation-Export.md`：T+ 对账导出。

实现时不得自行改变本文件已明确的状态、权限边界、必填条件或统计口径。文档间发生实质冲突时必须停止相关功能实现并报告，不得静默选择。

## 2. 项目目标

建立公司内部统一的资产管理系统，取代财务、设备部等部门各自维护且口径不一致的资产台账。

系统上线时不把现有两份旧台账当作权威迁移源，而是通过现场重新盘点、重新建档建立新的公司资产总账。旧台账仅用于历史查证。

核心目标：

1. 明确公司有哪些资产、在哪里、由谁负责。
2. 统一财务、设备部、生产及各部门的资产主数据。
3. 维护固定资产原值、累计折旧、减值及净值。
4. 支持部门盘点、财务全盘及专项盘点，并闭环处理差异。
5. 管理设备预防性保养及异常跟进。
6. 永久保留资产变动、盘点、保养、处置及财务变更历史。
7. 员工离职时检查并清理其名下资产。
8. 月末导出固定资产和折旧数据与用友 T+ 人工核对。

## 3. 系统定位与边界

EAM-Lite = 资产实物管理 + 固定资产辅助核算 + 二维码盘点 + 预防性保养。

正式会计凭证仍在用友 T+ 完成。V1.1 数据流为：

EAM-Lite 管理并计算 → 生成受控 Excel → 财务与 T+ 核对 → 财务在 T+ 人工记账。

禁止直接读取或修改 T+ 数据库，禁止通过 API 向 T+ 写入，禁止自动生成或过账会计凭证。

V1.1 不建设通用审批引擎。本文所称“提交”“财务确认”“贴标确认”“盘点关闭”等均是有权限人员直接完成的业务状态确认，不产生审批单、审批节点、同意/驳回链路，也不对接钉钉。

## 4. 使用规模、部署与技术约束

- 初始管理约 150 项资产。
- 设计容量至少为 5,000 项资产、100 个用户。
- 部署在公司 Wi-Fi / 局域网内的 Web 系统。
- 支持 PC 端 Chrome、Edge 及手机浏览器。
- 推荐技术栈：Python、Django、PostgreSQL、Bootstrap、HTMX、Django Templates。
- Excel 导入导出和二维码为 V1.1 必备能力。
- 不因初始数据量小而取消数据库唯一约束、并发控制、权限或审计。

## 5. 管理范围与两套分类

### 5.1 管理范围

V1.1 管理：

- 财务固定资产；
- 受控低值资产；
- 生产设备；
- 电脑和办公设备；
- 模具、工具、检具；
- 其他需要编号、责任人、位置、二维码、盘点、调拨或处置的实物资产。

受控低值资产即使不计提固定资产折旧，仍进入完整实物生命周期。

### 5.2 实物分类

`Asset.category`（界面标签“实物分类”）用于回答“这是什么实物”，是所有待提交资产的必填字段，采用可扩展树形结构。示例包括生产设备、模具、工具、检具、电脑、办公设备和其他；数据库不另建名为 `physical_category` 的重复字段。

实物分类可以配置：

- 分类编码及名称；
- 上级分类；
- 默认编码方案；
- 默认是否需要保养；
- 默认财务政策建议值。

实物分类中不得出现“固定资产”“低值资产”等会计认定结果。

编码片段 `custom_field` 仅为未来版本预留，V1.1 不实现其取值器，也不得在页面、导入模板或 API 可选项中暴露。V1.1 需要自定义常量时只能使用编码方案内直接配置的固定文本片段。

### 5.3 会计认定与固定资产类别

会计认定由财务单独维护，用于回答“会计上如何处理”，取值固定为：

- `unconfirmed`：未确认的页面/流程显示态，仅允许草稿或待财务确认阶段；数据库 `AssetFinance.accounting_treatment` 以 NULL/尚无 Finance 行表示，不保存该字符串；
- `fixed_asset`：财务固定资产；
- `controlled_non_fixed`：受控但不作为固定资产核算。

所有通过财务确认成为正式资产的记录都必须填写原值，原值允许为 0 但不得为空或小于 0。当会计认定为 `fixed_asset` 时，必须另选 `fixed_asset_category`，并建立财务资料和折旧配置；当认定为 `controlled_non_fixed` 时，不得填写固定资产类别或生成自动折旧，V1 的累计折旧和减值固定为已确认的数值 0，不能保存空值或其他金额。

实物分类与会计认定是两个独立维度。例如“模具”可以被认定为固定资产，也可以被认定为受控非固定资产。系统不得依据实物分类自动完成会计认定。

当前 5,000 元仅是可配置提示阈值：高于或等于阈值但认定为非固定资产时，财务必须填写认定说明；低于阈值仍允许财务明确认定为固定资产。系统不得自动认定。

### 5.4 保养属性独立

“是否需要保养”是资产级独立属性。实物分类只能提供默认值，创建资产时可以由设备角色调整并留痕。固定资产与是否保养之间不得建立强制等同关系。

## 6. 资产主档与数量规则

### 6.1 基础字段

- 系统内部唯一 ID；
- 正式资产编号；
- 资产名称；
- 实物分类；
- 品牌、型号、厂家；
- 序列号、出厂编号、历史编号；
- 数量、单位；
- 部门、责任人、位置；
- 购置日期、达到可使用状态日期；
- 是否需要保养；
- 封面图片、附件、备注；
- 资产状态、记录状态、标签状态；
- 创建人、修改人及时间。

资产编号在财务确认前为空。页面必须显示内部草稿号，不得用预览编号冒充正式编号。

### 6.2 单件追踪

V1.1 所有正式资产均按单件追踪：一个资产记录只代表一个实物，一个正式编号和一个二维码只对应这一件实物。

1. 数量字段固定为数值 1，新增和编辑页面均只读；后端、导入及数据库约束同样拒绝其他值。
2. 相同资产有多件时，必须建立多条独立草稿，并分别完成财务确认、编号和贴标。Excel 导入可以复制多行，但不得用一行数量大于 1 代表多件。
3. 调拨、借出、盘点、保养和处置均作用于完整的单件资产记录，不支持部分数量操作。
4. 批量数量管理、批量记录拆分及部分数量调拨/盘点/处置明确不在 V1.1 范围内。

## 7. 责任、部门与位置

- 位置使用不限层级的树状结构；当前业务至少支持“厂区 → 区域/车间 → 具体位置”。
- 正式启用为“在用”或“闲置”的资产必须有部门、责任人和具体位置。
- 大型共用设备仍必须指定一名责任人。
- 部门、责任人和位置不得通过直接覆盖字段完成变更，必须通过调拨/责任人变更/位置变更动作写入 `AssetMovement`，并同步更新主档当前值。
- 生效记录必须包含变更前值、变更后值、生效日期、操作人、原因和备注。
- 状态为 `leaving`、`resigned` 或已停用的人员不得被选为新的资产责任人，也不得通过领用、调拨、责任人变更或内部借用接收任何新资产；跨部门人员不满足授权范围时同样不得被选中。前端候选列表过滤和后端动作校验必须同时执行。

## 8. 初始化建账

### 8.1 标准流程

现场确认实物 → 建立草稿 → 上传资产照片 → 填写实物和使用信息 → 提交财务确认 → 财务明确会计认定并补充财务信息 → 系统事务内生成正式编号和二维码 Token → 打印标签 → 现场扫码或在 Web 资产页逐项确认贴标 → 在用或闲置。

### 8.2 状态与必填条件

1. **草稿 `draft`**：只有内部草稿号；允许反复编辑。至少填写资产名称、实物分类、单位、部门、责任人、位置及一张资产照片后才能提交；数量由系统固定为 1。
2. **待财务确认 `pending_finance`**：提交后继续保持数量 1；财务补充或核对会计认定和原值。无论认定为固定资产还是受控非固定资产，原值都必须为不小于 0 的已填写数值；累计折旧和减值允许为 0。提交人在财务确认前可撤回到草稿；财务发现资料不完整时可标记更正原因并退回草稿。
3. **待贴标 `pending_label`**：财务确认成功时，在同一数据库事务中生成且占用正式编号、二维码身份和安全 Token。已占用编号永不回收。正式记录不得回到草稿。
4. **在用 `in_use` / 闲置 `idle`**：标签打印后必须逐项确认实际贴标。操作人可扫描当前标签，或在有标签操作权限的 Web 资产页查看当前二维码并勾选确认。两种方式都必须再次校验部门、责任人、位置、当前有效二维码身份和 `printed` 状态，并由操作人选择初始状态“在用”或“闲置”。

财务确认是固定资产认定的业务确认点，不是审批流程：不创建审批单，不配置审批人，不提供通用“同意/拒绝”引擎。

### 8.3 Excel 初始化导入

批量导入固定执行：上传 → 解析 → 校验 → 预览 → 显示行级错误 → 用户确认 → 创建草稿。

- 导入不得直接生成正式编号、二维码或正式资产。
- 错误必须显示行号、字段、原值和原因。
- 导入草稿仍须补齐照片、责任人和位置，并走财务确认及贴标流程。

## 9. 资产完整状态机

### 9.1 状态定义

| 状态值 | 中文名称 | 说明 |
|---|---|---|
| `draft` | 草稿 | 尚未提交财务确认，无正式编号 |
| `pending_finance` | 待财务确认 | 等待财务明确会计认定 |
| `pending_label` | 待贴标 | 已正式编号，尚未完成现场贴标 |
| `in_use` | 在用 | 正常投入使用 |
| `idle` | 闲置 | 仍在管但当前未使用 |
| `loaned` | 借出 | 已借给内部或外部使用方，等待归还 |
| `under_repair` | 维修中 | V1.1 仅记录占用状态，完整维修工单属于 V2 |
| `pending_disposal` | 处置处理中 | 正在执行报废、出售或其他处置 |
| `disposed` | 已报废 | 报废完成的终态 |
| `sold` | 已出售 | 出售完成的终态 |
| `other_disposed` | 已其他处置 | 非报废、非出售的其他处置终态 |

`record_status` 与资产状态分离，仅取 `active` 或 `archived`。归档不代表报废，只有已报废、已出售、已其他处置的终态资产才能归档；正式资产永不物理删除。

### 9.2 允许的转换

| 当前状态 | 操作 | 目标状态 | 关键条件 |
|---|---|---|---|
| 草稿 | 提交财务确认 | 待财务确认 | 资料及资产照片完整 |
| 待财务确认 | 撤回/更正 | 草稿 | 尚未财务确认，记录原因 |
| 待财务确认 | 财务确认 | 待贴标 | 会计认定和原值完成；固定资产的固定资产类别及折旧资料完整；事务内生成编号和 Token |
| 待贴标 | 确认贴标并启用 | 在用或闲置 | 标签已打印；扫描当前标签或在 Web 资产页逐项勾选确认；部门/责任人/位置完整 |
| 在用 | 闲置 | 闲置 | 记录原因和生效日期 |
| 闲置 | 启用 | 在用 | 记录原因和生效日期 |
| 在用/闲置 | 借出 | 借出 | 内部借用人或外部借用方结构化信息、预计归还日、经办人完整；内部借用人必须为在职员工 |
| 借出 | 归还 | 借出前状态 | 记录实际归还日、接收人和位置 |
| 在用/闲置 | 送修 | 维修中 | 记录送修日期、经办人和说明 |
| 维修中 | 维修完成 | 送修前状态 | 记录完成日期和结果；V1.1 不生成维修工单 |
| 在用/闲置/维修中 | 发起处置 | 处置处理中 | 处置类型、原因、经办人完整；借出资产须先归还 |
| 处置处理中 | 取消处置 | 发起前状态 | 尚未完成处置；填写取消原因 |
| 处置处理中 | 完成处置 | 已报废/已出售/已其他处置 | 财务快照、日期、证据及必填字段完整 |

禁止其他直接状态跳转。终态发现操作错误时，不得编辑或删除原处置记录；财务必须执行“处置冲销”，填写原因，在不存在后续业务记录时恢复到处置前状态。原处置及冲销记录永久保留。

## 10. 财务属性与折旧

### 10.1 财务字段

仅授权财务可写：

- 会计认定、固定资产类别；
- 原值、入账日期、达到可使用状态日期；
- 折旧起始时间、折旧方法、使用年限；
- 残值率或残值金额；
- 期初累计折旧、本系统累计折旧、总累计折旧；
- 净值、减值、折旧暂停/恢复/终止信息；
- 财务调整、处置财务快照及处置收入。

财务字段的查看、导出和修改权限以 `docs/07-Permissions-and-Workflows.md` 为准，后端必须执行同样校验。

### 10.2 折旧方法与默认值

V1.1 必须支持：

- 年限平均法；
- 工作量法；
- 双倍余额递减法；
- 年数总和法；
- 手工折旧；
- 不计提折旧。

折旧政策优先级固定为：单项资产配置 > 实物分类默认政策 > 系统默认政策。分类默认只提供建议值，资产级最终配置仍由财务确认。

折旧起始规则支持当月、次月、指定月份、指定日期；周期支持月和年。当前公司默认残值率 5%、达到可使用状态次月起算、按月计提，三项均必须可配置，不得硬编码。

### 10.3 旧资产承接

旧资产初始化支持：

- A：录入财务确认的实际历史累计折旧并承接；
- B：系统计算理论历史折旧，供财务参考后确认。

系统必须分别保存理论累计折旧和实际累计折旧，不得以理论值自动覆盖账面值。已确认折旧历史不得直接改写，错误通过冲销、调整或新有效期配置处理。

所有金额使用 Decimal。具体舍入、尾差、双倍余额递减转直线、暂停恢复、减值后折旧、批次确认和冲销规则遵守 `docs/02-Business-Rules.md`。

## 11. 二维码与贴标

### 11.1 二维码身份

- 每个正式资产记录拥有一个当前有效的随机安全 Token。
- 二维码只编码公司局域网内的安全 URL 和 Token，不包含资产名称、责任人、位置、金额等明文资料。
- 扫码后仍执行登录、角色、数据范围和字段权限检查。
- Token 必须不可预测、唯一，并可被吊销。
- 有标签操作权限的用户可在资产详情、标签队列和已打印批次中查看当前二维码缩略图；二维码响应必须登录、按资产范围鉴权且禁止缓存。

### 11.2 标签状态

| 标签状态 | 含义 |
|---|---|
| `not_generated` | 尚未财务确认，无二维码身份 |
| `ready_to_print` | 已生成正式编号和 Token，等待打印 |
| `printed` | 已记录打印批次，等待现场确认 |
| `attached` | 已扫描当前标签或在 Web 资产页逐项确认贴标 |

财务确认后标签状态为 `ready_to_print`；加入 A4 打印批次并确认打印后为 `printed`；扫描当前 Token 或在 Web 资产页逐项勾选“确认已贴标”后为 `attached`。Web 确认不得批量跳过实物核对，且必须与扫码确认使用同一权限、资料完整性、当前二维码、幂等和审计校验。

贴标前因打印失败再次打印使用同一 Token，并记录打印批次。已贴标资产发生标签损坏或遗失时必须使用“换标”：填写原因、吊销旧 Token、生成新 Token、状态回到 `ready_to_print`。资产业务状态保持不变，旧二维码扫码只显示“标签已失效”。

V1.1 支持 A4 批量打印，不适配专用标签打印机。

## 12. 资产变动、领用、借出与归还

- 部门、责任人、位置变化统一通过变动操作，不允许在正式资产编辑页直接覆盖。
- 领用、归还、部门调拨、责任人变更、位置变更、借出及借出归还均生成不可删除的历史记录。
- V1.1 不审批；具备操作权限的用户直接执行并写审计日志。
- 所有变动均作用于完整的单件资产记录，不提供数量输入或部分变动。
- 变动完成后，资产详情页当前值与历史最后一条生效值必须一致。

借出必须先选择借用方类型：

- `borrower_type=internal_employee`：必须保存结构化 `borrower_employee` 关联，`borrower_name` 和 `borrower_organization` 必须为空，并由服务端另存不可编辑 `borrower_name_snapshot`；借用人姓名和部门仅从员工主数据展示，不允许以手填姓名替代。员工必须属于当前公司且满足 `employment_status='active' AND is_active=true`。
- `borrower_type=external`：`borrower_employee` 必须为空，`borrower_name` 必填、`borrower_organization` 可空；只有该类型允许手填姓名和单位。

两种类型互斥。状态为 `leaving`、`resigned` 或已停用的员工不得新领用、新接收转交或成为内部借用人，任何批量入口、导入入口和直接 API 调用都必须按同一规则拒绝。

## 13. 盘点闭环

### 13.1 类型与范围

类型固定为部门盘点、财务全盘、专项盘点。范围可按全公司、部门、实物分类、位置或勾选资产确定。

盘点任务状态固定为：

- `draft`：编辑范围和人员；
- `in_progress`：已发布并扫码；
- `reconciliation`：停止扫码并处理差异；
- `closed`：差异已形成处理结论；
- `cancelled`：发布前取消，或发布后由有权用户带原因取消。

### 13.2 快照与扫码

任务发布时生成应盘资产快照，保存当时的部门、责任人、位置和状态。任务发布后快照不得因资产调拨而变化，也不得删除快照行。

扫码结果固定为：正常、位置异常、责任人异常、状态异常、多项异常、其他异常。位置、责任人、状态分别与发布快照比较；同时有两项或三项不一致时使用“多项异常”并逐维保留全部现场值，不得只选一个后丢失其他差异。系统内存在但不属于任务快照的二维码显示“非本任务资产”，不得计入已盘。系统中不存在的实物必须建立独立“盘盈待确认”记录，不得伪造资产 ID；盘盈记录至少包含临时名称、发现位置、发现人和照片。

重复扫描全部保留历史，最后一次被明确标记为“有效结果”的扫描决定当前盘点结果。

### 13.3 差异处理与关闭

盘点停止后，未扫描资产先标记“未盘”。核查后必须选择：补盘、确认盘亏、确认不在本次现场但保留资产，且填写说明。

位置、责任人或状态异常不得自动修改主档。处理人必须选择：

- 按盘点实际执行正式变动并关联变动记录；
- 确认主档无误并填写差异原因；
- 转入其他明确处理动作。

盘盈由财务直接确认处理结论：转资产草稿、非公司资产、重复记录或其他。转草稿后仍走完整初始化流程。

只有所有快照行已形成结果、所有差异已有处理结论、所有盘盈已有处理结论后才能关闭任务。关闭后结果不可编辑；纠错必须创建有原因的更正记录。系统生成盘点结果表及盘点差异表。

## 14. 员工离职资产清退闭环

1. HR 将员工状态改为 `leaving` 时，系统自动创建清退单，快照该员工在发起时当前负责的所有非终态资产，以及以 `borrower_employee` 结构化关联到该员工的所有未归还内部借用资产。
2. 员工进入 `leaving` 后，系统立即禁止其接收任何新领用、转交、调拨或内部借用资产；该禁止规则不得因存在未完成清退单而绕过。
3. 清退未完成期间，动态刷新只允许补入“关联关系在清退发起时间之前已存在，但发起后才被发现，或因既有关联资产状态变化而变为应清退”的资产。补入项必须记录原关联生效时间、发现时间和补入原因；不得把清退发起后的新领用、转交、调拨或借用当作动态补入路径。
4. 每项资产必须选择并实际完成：归还、转交、处置。
5. 归还必须指定接收部门、接收责任人和位置，完成后资产进入闲置或在用；转交必须产生责任人/部门/位置变动；处置必须关联已完成的处置记录。终态资产保留的最后责任字段仅供历史显示，不再构成活动领用关系，因此 confirmed 处置可解决 Item，但借用资产仍必须先归还。
6. 清退单显示总数、已处理数、未处理数及每项证据。HR 无权直接把未处理项强制标记为完成。
7. 未处理数为 0 后，HR 必须填写实际离职日期（不早于入职日、不晚于当前上海业务日），系统才在同一事务关闭首次清退、写入 `termination_date` 并将员工状态改为 `resigned`；否则后端阻止并显示明确警告。
8. 已完成后发现遗漏资产时，原单和原离职日期不得改写。HR 填写原因建立一张指向原单的补充清退；员工保持 resigned，补充单仅处理遗漏资产并独立完成，同员工仍最多一张活动清退。

清退记录、补充关系及项目快照永久保留。

## 15. 设备预防性保养闭环

V1.1 只做预防性保养，不做完整故障维修工单。

### 15.1 保养计划

计划包括资产、计划名称、周期数值、周期单位、责任人、首次到期日、上次完成日、下次到期日、标准内容、提前提醒天数和状态。

V1.1 周期单位仅支持日、周、月、年。按运行小时保养需要设备运行时读数，明确放入 V2，不得在 V1.1 页面暴露不可用选项。

计划状态为启用、暂停、终止。首次下次到期日取首次到期日；此后只根据上一条已确认完成记录计算。修改周期只影响未来到期日，不改写历史记录。资产完成处置时自动终止未结束计划。

### 15.2 提醒、完成与异常

- 今天处于 `[下次到期日 - 提前提醒天数, 下次到期日]` 时为“即将到期”。
- 今天晚于下次到期日且没有对应已确认完成记录时为“逾期”。
- 完成记录包括计划日期、实际完成日期、完成人、实际内容、结果、发现问题、照片/附件和备注。
- 结果为“发现问题”时，问题说明必填，并形成待跟进项；equipment 或范围内 department_manager 填写处理说明并关闭跟进项。V1.1 仅跟踪说明及关闭，不扩展为维修工单。
- 已确认完成记录不可直接编辑；错误记录须作废并重新建立，作废记录仍保留。
- 来源完成记录被作废后，其问题和附件保留为历史，但不再进入当前 open 待办，也不能伪造关闭结果；重建后如再次发现问题，形成属于新记录的新问题。
- 只有已确认且未作废的完成记录才更新上次完成日和下次到期日。

## 16. 报废、出售与其他处置闭环

### 16.1 发起

处置类型固定为报废、出售、其他处置。发起时填写处置类型、申请日期、拟处置日期 `planned_disposal_date`、原因、说明、经办人和接收方（如有），资产状态变为“处置处理中”，并保存发起前状态。拟处置日期只用于计划和提醒，不得据此生成财务快照、进入终态或停止折旧；发起时实际完成日期 `actual_disposal_date` 必须为空。

借出资产必须先归还。每次处置作用于完整的单件资产记录，不提供部分数量处置。

### 16.2 财务快照与完成

实物处置发生后，有完成权限的设备或财务人员先填写实际完成日期 `actual_disposal_date`；该日期不得早于申请日期、不得晚于当前上海业务日。财务随后以实际完成日期为截止日，从权威财务数据核对并锁定原值、累计折旧、减值、净值和处置收入，普通业务用户不得手填快照金额。实际完成日期为空时不得锁定快照；快照未锁定时不得完成处置。

财务快照锁定后，实际完成日期和快照金额均不可直接修改，完成动作必须复用同一实际完成日期。锁定后发现日期错误时，只能带原因取消本次未完成处置并重新发起，原记录、锁定值和审计仍保留。

- 报废：实际完成日期在页面显示为“报废日期”，原因、经办人及至少一张报废现场照片必填；
- 出售：实际完成日期在页面显示为“出售日期”，接收方、处置收入及至少一份出售证据必填；
- 其他处置：实际完成日期在页面显示为“实际处置日期”，原因、接收方/去向及至少一份处置证据必填。

完成后分别进入已报废、已出售、已其他处置终态；终态生效日和停止后续折旧的截止口径均使用上述实际完成日期，随后终止保养。终态资产从活动领用、人员在用清单和业务候选中排除，但 `Asset` 上最后责任人、部门和位置不清空，仅作历史显示；这不再构成活动领用关系。拟处置日期、实际完成日期、财务快照和附件同样永久保留。

处置处理中可以带原因取消并恢复发起前状态。终态纠错仅允许按第 9.2 节执行处置冲销，禁止删除或覆盖。

## 17. 附件

### 17.1 支持场景

附件必须可以关联到以下业务对象，而不是强制都依赖已正式化的资产：

- 资产草稿/正式资产：照片、发票、合同、验收单、说明书、合格证、其他；
- 盘点扫描：差异证据；
- 盘盈记录：现场照片及说明材料；
- 保养记录及问题跟进：照片、保养单、检测材料；
- 处置记录：报废照片、出售或移交证据；
- 离职清退项目：归还、转交或处置证据。

盘盈记录在转为资产草稿前即可上传照片；转草稿后原附件仍保留在盘盈记录，并可按关联关系在草稿中查看，不得丢失或复制成无来源文件。

### 17.2 安全与文件规则

- 附件保存在非公开目录，下载必须校验其所属业务对象权限。
- 发票、合同、验收单和所有财务附件只对财务及获准查看财务信息的管理层显示。
- 默认允许 JPG、JPEG、PNG、WEBP、PDF、XLSX、DOCX；单文件不超过 20 MB。
- 禁止可执行文件、脚本、宏文档和 SVG；不得只按扩展名判断类型。
- 删除仅允许删除尚未提交草稿中的误传附件；已进入正式业务流程的附件只能作废并保留元数据、原因和审计日志。
- 每个文件记录原文件名、存储名、MIME 类型、大小、上传人、上传时间、用途、关联对象和作废状态。

## 18. Excel 导入、报表与 T+ 对账导出

### 18.1 通用导出

V1.1 提供：

- 公司资产总账；
- 固定资产明细；
- 折旧明细；
- 部门资产、人员资产；
- 设备清单、模具工具清单；
- 盘点结果、盘点差异；
- 保养计划、保养记录；
- 报废/出售/其他处置清单。

导出必须应用与列表查询相同的数据范围和字段权限。金额保持 Excel 数值单元格，日期保持日期单元格，不得全部导出为文本。

### 18.2 T+ 对账导出

固定资产月末对账导出只允许财务角色执行，必须包含导出期间、导出时间、导出人、口径版本及可复核的资产/折旧明细。不得向 T+ 自动写入。

字段映射、期间锁定、文件结构、差异核对及验收以 `docs/11-Tplus-Reconciliation-Export.md` 为唯一详细规范。

## 19. 权限

系统角色固定为：

- `system_admin`
- `finance`
- `equipment`
- `department_manager`
- `employee`
- `warehouse`
- `hr`
- `management`

同一用户可以拥有多个角色，权限按允许项合并，但财务字段不会因 `system_admin` 身份自动开放。所有列表、详情、扫码、导入、导出、附件和操作接口必须在后端执行公司范围、部门范围、本人范围及字段级权限校验。

完整角色矩阵和业务动作归属见 `docs/07-Permissions-and-Workflows.md`，该文件是实现权限的验收依据。

## 20. 首页指标

首页所有数量按当前用户数据范围统计；财务金额卡仅对 `finance` 和 `management` 显示。

### 20.1 财务卡片

- 固定资产原值：截至查询日仍在账固定资产的确认原值合计；
- 累计折旧：截至查询日全部已过账原始、期初、调整和反向分录的代数和（即冲销后的净额，原分录仍保留）；
- 净值：原值减累计折旧、减值及已确认价值调整后的合计；
- 本月折旧：当前自然月全部已过账原始和反向分录的代数净额。

### 20.2 实物卡片

- 资产总数：已有正式编号且状态为待贴标、在用、闲置、借出、维修中或处置处理中的在管记录数；草稿、待财务确认和三个终态不计入；
- 在用：状态为 `in_use` 的记录数；
- 闲置：状态为 `idle` 的记录数；
- 报废：状态为 `disposed` 且未被处置冲销的累计记录数。

首页不得把“本月新增”替代“报废”。本月新增可以在报表筛选中查看，但不是 V1.1 实物卡片。

### 20.3 待办卡片

- 待财务确认：`pending_finance` 记录数；
- 待贴二维码：正式且非终态资产中标签状态不是 `attached` 的记录数；
- 待盘点：进行中任务快照里尚无有效扫描结果的记录数；
- 盘点异常：尚无处理结论的盘点差异与盘盈记录数；
- 即将保养：处于提前提醒区间且未完成的启用计划数；
- 逾期保养：已过下次到期日且未完成的启用计划数；
- 离职资产未清：所有未完成清退项目数。

部门和实物分类图表使用与“资产总数”相同的在管资产口径。

## 21. 审计、备份与非功能要求

### 21.1 审计

关键业务从首个 Sprint 起记录操作人、时间、对象、动作、修改前值、修改后值、来源 IP 和必要原因。至少覆盖基础资料、编码规则、财务确认、标签、资产变动、折旧、盘点、保养、离职清退、处置、附件作废和权限变更。

Sprint 11 提供只读操作日志查询：system_admin 看公司全域；finance 仅本人及财务对象；hr 仅人员/清退对象及本人 HR 动作；其他角色默认拒绝。查询结果继续按字段权限脱敏，任何角色都不能通过页面修改、删除或导出 AuditLog。

### 21.2 备份

- 每日备份数据库和附件目录；
- 至少保留最近 30 天日备份；
- `system_admin` 可手动下载备份；
- 提供并实际验证恢复说明；
- 备份下载动作写入审计日志。

### 21.3 非功能要求

- 中文界面、手机响应式；
- 财务金额全程使用 Decimal；
- 密码安全哈希存储，密钥不进入代码库；
- 附件受保护且限制类型、大小；
- 正式资产、已确认折旧和正式附件不物理删除；
- 关键业务规则有自动测试；
- 5,000 元、5% 残值率、编码格式均可配置，不得硬编码。

## 22. V1.1 明确不做

- 通用审批引擎、钉钉审批和钉钉消息；
- 批量数量资产记录、记录拆分及部分数量调拨/盘点/处置；
- T+ API、T+ 数据库写入、自动凭证；
- 公网部署；
- 完整故障维修工单；
- 按运行小时保养；
- 税务折旧；
- RFID；
- 专用标签打印机适配；
- MES、采购管理、通用物料库存。
