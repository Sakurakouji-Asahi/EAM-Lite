# Asset Coding Rules V1.1

本文件是正式资产编号的规范性定义。实现、测试和并发验收均以本文件为准；示例不是固定编码格式。

## 1. 目标与边界

- 资产编码格式由管理员配置，不写死在 Python、模板或数据库触发器中。
- V1 采用单公司运行，但所有方案、计数器和已发编号都必须带 `company_id`。任何跨公司引用均拒绝。
- 草稿可以没有正式编号；只有既存的 `Asset` 记录才能申请正式编号。
- 正式编号一旦发出即永久占用。更正、作废、归档、处置、回滚业务状态以及删除草稿都不能释放编号。
- `IssuedCode` 是“这个字符串曾被正式使用”的权威登记；仅在当前 `Asset` 上做唯一约束不够。
- 编号只标识资产，不表达会计认定。物理资产大类/小类来自 `AssetCategory`，不得用固定资产会计类别代替。

## 2. 编码方案与版本

### 2.1 方案身份

`AssetCodingScheme` 的一个数据库行代表一个不可变的具体版本，至少包含：

- `company_id`
- `scheme_key`：同一方案各版本共用的稳定键
- `version`：从 1 开始的整数
- `name`、`description`
- `status`：`draft` / `active` / `retired`
- `is_default`
- `effective_from`、`effective_to`
- `reset_mode`
- `sequence_start`
- `category_scope_level`
- `previous_version_id`
- 创建人和时间

数据库唯一约束为 `(company_id, scheme_key, version)`。同公司同一 `scheme_key` 的版本必须形成单向链，禁止循环。

### 2.2 生命周期

1. `draft` 版本可以修改并校验，但不能发正式编号。
2. 启用前必须通过全部结构校验，并确保生效期不与同一 `scheme_key` 的其他活动版本重叠。
3. 只要该版本存在一条 `IssuedCode`，方案、片段、顺序、流水设置和格式设置全部锁定。
4. 修改已使用方案时必须执行“克隆为新版本”：复制方案和全部片段，`version + 1`，新行状态为 `draft`。
5. 新版本启用后，旧版本改为 `retired` 或设置 `effective_to`；旧资产继续引用原版本，旧计数器和已发编号不迁移、不重算。
6. 删除仅允许用于从未发号且未被任何类别或资产引用的 `draft` 版本。其他版本只能停用/退役。

### 2.3 方案选择

正式发号时在同一事务内按以下优先级解析一个“具体版本”：

1. 资产草稿上由授权管理员明确选择的活动版本；
2. 资产物理类别绑定的活动默认版本；
3. 公司唯一的活动默认版本。

未找到、找到多个默认版本、生效日期不匹配、公司不一致或方案已退役时必须失败，不得静默换用其他规则。选中的具体版本永久写入 `IssuedCode`。

## 3. 可用片段

每个片段有稳定顺序 `sequence_order`，同一方案内唯一。V1 支持：

| `segment_type` | 输出来源/说明 |
|---|---|
| `fixed_text` | 管理员配置的固定文字 |
| `company_code` | `Company.code` |
| `major_category_code` | 物理分类路径中的资产大类代码 |
| `minor_category_code` | 物理分类路径中的资产小类代码 |
| `category_code` | 当前叶级 `AssetCategory.code` |
| `department_code` | 发号时资产所属部门代码 |
| `year` | 生效日期的 `YYYY` |
| `year_month` | 生效日期的 `YYYYMM` |
| `full_date` | 生效日期的 `YYYYMMDD` |
| `sequence` | 当前作用域正式流水号 |
| `custom_text` | 方案中直接配置的自定义常量 |
| `separator` | 明确配置的分隔符 |

`custom_field` 不属于 V1 可用片段。V1 没有经过批准的自定义字段来源模型、字段白名单或取值时点，因此配置页面、导入模板和 API 均不得显示/接受 `custom_field`。数据库枚举或代码可以为未来迁移预留该名称，但 V1 规则校验必须明确拒绝，不能把任意模型属性、JSON 路径或动态 `getattr` 当作替代来源。未来启用必须先修订本规范并定义稳定来源、公司范围、缺值行为和历史版本语义。

资产大类/小类按分类树路径解析，不能用名称猜测：

- `major_category_code` 为该公司分类树的一级分类代码；
- `minor_category_code` 为二级分类代码；
- 路径没有所需层级时发号失败；
- 会计 `FixedAssetCategory` 不参与上述解析。

片段原始大小写按主数据保存并输出；系统不在发号时偷偷改变大小写。为避免视觉重复，正式代码的唯一性按规范化值作不区分大小写校验。

## 4. 流水设置

### 4.1 起始值和补零

- 每个方案必须恰有一个 `sequence` 片段。
- `sequence_start` 是该作用域首次正式发出的数字，而不是计数器初值。例如起始值 1，首次发号就是 1。
- 新计数器保存的初始 `current_value = sequence_start - 1`；正式发号时先加 1，再格式化。
- `sequence_start` 必须为 0 或正整数。
- `sequence_length` 为正整数，V1 建议 1–12。
- `zero_pad=true` 时使用 ASCII `0` 左侧补齐；`sequence_length=5`、数值 23 输出 `00023`。
- `zero_pad=false` 时直接输出十进制数值，`sequence_length` 只作为允许最大位数的校验上限，不填空格。
- 数字位数超过 `sequence_length` 时必须报“流水号已溢出”并回滚，禁止截断、扩位或回到起始值。

### 4.2 重置模式

V1 支持：

- `never`
- `yearly`
- `monthly`
- `category_yearly`
- `category_monthly`

公司始终是隐含作用域；即使 V1 只有一家公司也不能省略。`category_*` 使用方案的 `category_scope_level`：`major` / `minor` / `leaf`。缺少该层级时拒绝发号。

日期一律以业务时区 `Asia/Shanghai` 的“正式编号生效日期”计算，不使用服务器本地时区，也不使用请求到达的 UTC 日期代替。财务确认页面显式显示该业务日期，默认当前上海日期；finance 必须确认，不能为未来日期。旧资产初始化需要历史日期时允许带原因回填。编号更正使用更正动作明确的生效日期并记录原因；不得偷偷沿用资产购置日或达到可使用状态日期。

## 5. `scope_key` 的规范构造

`scope_key` 只用于计数器定位，不显示给用户。它必须由不可变数据库标识构造，不能依赖可能改名的代码文本。

推荐先生成有固定字段顺序的规范 JSON，再保存其可读串或 SHA-256：

```json
{"company_id":"<uuid>","scheme_id":"<uuid>","reset":"monthly","year":2026,"month":8}
```

各模式包含：

| 模式 | `scope_key` 组成 |
|---|---|
| `never` | company ID + concrete scheme-version ID |
| `yearly` | 上述字段 + 四位年份 |
| `monthly` | 上述字段 + 四位年份 + 两位月份 |
| `category_yearly` | 上述字段 + 分类层级 + 对应分类 ID + 年份 |
| `category_monthly` | 上述字段 + 分类层级 + 对应分类 ID + 年份 + 月份 |

即使 `scope_key` 已包含这些信息，`SequenceCounter` 仍必须保存独立的 `company_id` 和 `coding_scheme_id`，并建立复合唯一约束：

`UNIQUE(company_id, coding_scheme_id, scope_key)`。

不得把资产名称、部门名称、当前计数值或可变类别代码放进作用域。方案新版本有新的 `scheme_id`，因此从该版本的 `sequence_start` 建立新计数器。V1 不预建或人工编辑 Counter；若业务希望新版本从某个后续数字继续，管理员必须在该 draft 版本启用前把 `sequence_start` 明确设为下一个可签发数字并审计版本配置，不能复制旧 current_value、自动猜测或绕过首次发号事务。

## 6. 正式发号事务

正式发号服务（例如 `AssetCodeIssuer.issue()`）必须在 PostgreSQL 的单个 `transaction.atomic()` 中完成：

1. 以 `SELECT ... FOR UPDATE` 锁定目标 `Asset`。首次发号必须处于未发号的 `pending_finance` 财务确认事务；编号更正必须由 `docs/07-Permissions-and-Workflows.md` 允许的独立更正动作发起。两者均须校验公司一致、显式编号生效日期及必需来源字段完整。
2. 按生效日期解析并锁定一个活动方案具体版本。
3. 构造规范 `scope_key`。
4. 采用 PostgreSQL `INSERT ... ON CONFLICT DO NOTHING` 幂等建立计数器行；随后按复合键 `SELECT ... FOR UPDATE`。禁止用“先查、未找到再普通插入”的竞态写法。
5. 将 `current_value` 原子加 1；检查起始值、上限和格式。
6. 渲染全部片段，生成显示代码及 `normalized_code`。
7. 插入 `IssuedCode`。数据库必须有 `UNIQUE(company_id, normalized_code)`。
8. 把该 `IssuedCode` 绑定到资产，并写入首次 `AssetCodeHistory` 和审计日志。
9. 一并提交；任一步失败，计数器、登记、资产和审计全部回滚。

并发插入计数器或代码发生唯一冲突时，可对整个发号事务做有限次数重试；每次必须重新读取方案和锁定计数器。不得仅重试最后一条 `INSERT`，不得返回未登记代码。

### 6.1 幂等

发号命令必须接收服务端生成的 `idempotency_key`，并在公司范围唯一。相同 key、相同资产重复请求返回原 `IssuedCode`；相同 key 指向不同资产或不同参数时拒绝。若资产已经有正式编号，普通重复提交返回现有编号，不再消耗流水。

允许出现事务回滚造成的无缺口恢复；系统不承诺编号连续。已经成功提交后即使后续业务失败，也禁止回收号码。

## 7. 已发编号和更正历史

### 7.1 `IssuedCode`

至少记录：

- 公司、方案具体版本、作用域、流水数值；
- 显示代码、规范化代码；
- 发号生效日期、历史回填原因（适用时）、发号时间、发号人；
- 幂等键；
- 状态：`active` / `replaced` / `voided`；
- 作废/替换原因及时间。

所有状态都永久占号。应用用户没有删除权限；数据库外键使用 `PROTECT/RESTRICT`。

### 7.2 `AssetCodeHistory`

每次首次发号、编号更正或明确作废均新增历史行，至少记录：资产、事件类型、旧 `IssuedCode`、新 `IssuedCode`、原因、操作人、业务生效时间和创建时间。历史行只追加。

V1 只允许更正非终态正式资产；终态/已归档记录发现编号问题必须报告并另行批准数据更正方案，不得触发无意义的重贴标。允许的编号更正必须执行新的完整发号事务：发出一个新 `IssuedCode`，旧登记改为 `replaced`，资产改绑新登记，并写一条同时指向新旧登记的历史。因为纸质标签上的编号已变化，同一事务还必须调用既有换标能力撤销旧 QR Token、创建新身份并进入 `ready_to_print`；资产业务状态不变。不得直接编辑字符串。若更正事务失败，旧编号、QR 和标签状态仍为当前有效版本。

## 8. 格式与输入校验

启用方案前至少校验：

- 片段非空、顺序连续且唯一；
- 恰有一个流水片段；
- `custom_field` 及其他非 V1 片段一律拒绝，且不出现在配置选项中；
- 所有来源在发号上下文可获得；
- 生效区间合法且默认方案唯一；
- 最大渲染长度不超过 64 个字符；
- 输出经 Unicode NFKC 规范化后不得为空；
- 禁止控制字符、换行、首尾空白、连续不可见字符以及 `{`、`}` 模板残留；
- 允许的分隔符仅为管理员白名单中的 `-`、`_`、`.`、`/`；
- 分类/部门/公司必须属于同一公司且处于可用于新业务的状态；
- 日期与重置模式所需字段完整。

显示值保留配置大小写；`normalized_code = NFKC(display_code).strip().casefold()`，用于永久唯一检查。

## 9. 预览

配置页实时显示一个示例，并提供“生成 10 个示例”。预览：

- 使用当前计数器快照或 `sequence_start` 在内存中模拟；
- 不创建或更新 `SequenceCounter`、`IssuedCode`、历史或审计业务记录；
- 明确标注“预览，不占号”；
- 必须使用与正式渲染相同的格式化和校验函数；
- 预览成功不代表正式发号必定成功，因为正式发号仍需重新校验主数据、权限、唯一性和并发状态。

## 10. 最低验收测试

除各种片段和五种重置模式外，必须在 PostgreSQL 覆盖：

1. 起始值 0、1 和自定义正整数的首号正确；
2. 补零开启/关闭及溢出回滚；
3. 大类、小类、叶级分类解析正确，缺层级拒绝；
4. 不同公司、方案版本、月份和分类的计数器互不串号；
5. 首次并发创建同一作用域计数器只产生一行；
6. 至少 20 个并发请求无重复编号、无重复流水登记；
7. 重复幂等请求只消耗一次流水；
8. 预览不消耗流水；
9. 已发、已替换和已作废代码均无法再使用；
10. 更正同时保留旧号、新号和原因；
11. 已使用版本不可编辑，克隆新版本后旧资产不变；
12. 大小写或 Unicode 兼容形式不同但规范化相同的代码发生唯一冲突；
13. 任一步异常时计数器、资产、登记和审计共同回滚；
14. 配置 UI/API 不提供 `custom_field`，构造该枚举的直接请求被后端拒绝；
15. SQLite 测试明确跳过/标记不支持的锁语义，不能替代 PostgreSQL 并发验收。
