# EAM-Lite V1.2 低值物品操作与月末核对

## 1. 使用边界

低值物品分为三种管理口径：

- `consumable`：领用后通常消耗，按物品和仓库管理数量与成本；
- `durable_quantity`：同类多件、无需逐件编号，领用后形成数量型保管责任；
- `controlled_non_fixed`：需要逐件编号、责任人、位置或二维码，继续使用
  `Asset + AssetFinance`，资产数量始终为 1，且不计提折旧。

本模块不是采购、生产物料或会计凭证系统。库存及保管金额是内部管理金额，T+ 仍是正式会计账。

## 2. 初始化顺序

1. 完成公司、部门、员工、位置及应用用户角色初始化。
2. 在“低值物品 → 分类”建立分类树。
3. 在“低值物品 → 仓库档案”建立仓库并选择可用负责人。
4. 建立数量型物品档案，明确管理模式、单位、最低库存和默认仓库。
5. 需要逐件管理的物品从“新增逐件低值耐用品”进入现有资产流程，由财务认定为
   `controlled_non_fixed`。

## 3. Excel 初始化

- 物品档案：下载固定模板，上传、校验、预览并整批确认。
- 仓库期初：确认后只生成期初单草稿；业务人员复核后再过账。
- 期初保管：用于已发放的数量型耐用品，确认后建立开放保管和不可变期初流水，不增加仓库库存。

只接受批准的 `.xlsx`。错误会标明行号、字段、原值和原因；任一无效行阻止整批确认。

## 4. 日常业务

- 日常入库：每行填写数量和单位成本；0 成本必须写原因。
- 领用：仓库成本按移动加权平均自动计算；耐用品同步建立保管记录。
- 退回：必须引用原领用；耐用品还必须引用当前开放保管，成本沿用来源快照。
- 调拨：来源与目标仓库同事务更新，调出和调入金额完全一致。
- 耐用品归还、转交、报损、报废：只从保管动作入口执行，全部写不可变流水。
- 已过账错误：优先走受控冲销；存在后续业务时按系统提示使用当前日期正常更正，不改历史。

## 5. 盘点与离职清退

- 仓库盘点发布后冻结对应仓库库存过账，关闭时自动形成盘点调整。
- 保管盘点差异必须引用真实归还、转交、报损、报废或 correction 流水。
- 员工离职清退同时包含逐件资产和个人数量型耐用品保管；易耗品历史领用不阻断离职。

## 6. 正式报表

“低值物品 → 正式报表”提供 12 张分页报表及完整 XLSX。Dashboard、页面和 Excel 调用同一查询口径。
不同单位数量分开显示，不跨“箱、把、个、套、公斤”合计。低库存只比较启用物品的默认仓库；未配置默认仓库的物品单独查看，不计入正式预警数。

无成本权限时，成本列不会进入数据库投影、HTML、模板上下文或 XLSX。导出记录保存公司、导出人、时间、筛选、实际行数、成本列范围、私有文件和 SHA-256。

## 7. 月末只读核对

先安排低值物品业务截止时间，由应用管理员执行：

```powershell
python manage.py reconcile_supply_balances --company <公司编码>
python manage.py reconcile_supply_custodies --company <公司编码>
```

两个命令只读。成功表示当前库存/保管缓存与不可变流水一致；失败时应保留完整输出并暂停相关业务排查。

## 8. 受控余额重建

只有确认是缓存差异、历史流水本身完整时，才申请维护窗口。先 dry-run：

```powershell
python manage.py rebuild_supply_balances --company <公司编码> --actor <用户名> --reason "<原因>"
python manage.py rebuild_supply_custodies --company <公司编码> --actor <用户名> --reason "<原因>"
```

核对差异后，在批准的维护窗口追加 `--confirm`。操作人必须是同公司启用的
`system_admin` 或 `finance`。库存重建先按仓库 UUID 锁仓库，再按仓库/物品锁余额；保管重建按
custody UUID 稳定锁定。活动盘点会阻止写入。提交后系统再次核对并写审计；重复确认幂等。

重建不会修改或删除库存流水、保管流水、单据、来源链或保管单位成本快照。业务人员不得直接改数据库、删除流水、删除保管记录、手改缓存或修改历史迁移。

## 9. 默认业务数据库正式升级

1. 获得人工部署审批并安排维护窗口；停止新业务写入。
2. 按现有运维手册完成数据库和附件同一恢复点备份，并确认备份可用。
3. 记录升级前 `showmigrations` 和 `migrate --plan`。
4. 在隔离恢复库先演练相同基线升级与 reconcile。
5. 由迁移身份执行正式 `migrate --noinput`；不要使用运行时最小权限身份迁移。
6. 执行 `check`、两项 reconcile、关键页面与导出抽查。
7. 验收通过后恢复业务；失败按既有恢复手册回退整个恢复点，不单独回滚业务流水。

本 Sprint 开发与 UAT 未对默认业务数据库执行迁移。

## 10. 性能验证命令

`benchmark_supply_reports` 默认拒绝写入，只允许名称含 `s18/perf/uat/test` 的空 PostgreSQL 数据库，并必须显式传入
`--confirm-non-production`。生成数据只用于可丢弃隔离库；验证后删除该精确隔离数据库，不触碰默认数据库或 Docker 卷。
